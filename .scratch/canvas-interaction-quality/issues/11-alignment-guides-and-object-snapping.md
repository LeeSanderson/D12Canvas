# Alignment guides and object snapping

Type: prototype
Status: resolved
Blocked by: 05

## Question

Design snap-lines to neighbouring objects during a drag or resize — the single largest gap between the current canvas and a tool that feels professional to lay out with.

Nothing of this exists today. The only snapping is `SnapToGrid` (ADR 0011), an off-by-default toggle that snaps to whichever adaptive grid layer is currently dominant, wired into `NewCenteredInstance` and the single-instance branch of `MoveComponent` only.

Build a prototype and decide:

- Which anchors participate: edges, centres, both. Whether equal-spacing detection between three or more objects is in scope, or only pairwise alignment.
- Snap tolerance, and whether it is measured in screen pixels or board units. Screen pixels keep the feel constant across zoom, which matters a great deal on ADR 0011's unbounded zoom range; board units keep behaviour reproducible. These genuinely conflict.
- Which candidates are considered. Scanning every instance is O(n) per mousemove on top of the live-geometry render cost from ticket 05. `Board.GetVisible(viewport, overscan)` already exists and bounds the set to what is on screen — decide whether that is sufficient, and what happens with a large selection dragged across a dense board.
- Composition with `SnapToGrid`. Both active at once, one suppressing the other, or a combined precedence. Ticket 72 of `d12canvas-next` deliberately kept grid snapping out of multi-selection and group moves because a shared delta snapped per-member would break `CommitGroupMove`'s relative-offset guarantee — object snapping faces the identical problem and cannot dodge it, since aligning a multi-selection is exactly the case users want.
- Whether it applies to resize as well as move, and to edge endpoints.
- Rendering: guides are chrome drawn in board space, appearing and disappearing per frame. Which layer, and how they read against both light and dark themes (ADR 0012's token set).
- A suppression modifier, so a user can place something deliberately unaligned.
- Whether guides are purely visual or actually alter the committed position, and how that lands in ADR 0007's gesture-level history.

**This ticket now owns the whole constrain-modifier vocabulary, not just its own suppression key** (added while resolving ADR 0022, which deliberately left the pointer's modifiers almost entirely unbound so they could be decided together rather than in three places). Three claimants, one budget:

- **Snap suppression**, this ticket's own. Ticket 03 found Ctrl is the "escape from automatic help" key in all four reference tools, and that it **inverts** rather than merely suppresses in both open-source ones. Ctrl is unbound on the pointer today precisely so this can take it.
- **Axis-locked movement** — constraining a drag to whichever axis moved further, which Excalidraw binds to `Shift`. ADR 0022 confirmed it composes with `Shift`'s selection meaning without a clash (below the 4-pixel drag threshold the press is a selection toggle, above it the `Shift` reads as a constraint and the toggle never happens), so the mechanism is free. It was routed here rather than bound there because axis-lock and snapping answer the same user question, and deciding them apart risks two "help me be precise" modifiers that were never designed together.
- **Pressing through content.** Not a constraint, but it wants the same key. A selection band can only start on empty canvas, and ADR 0017 widened that hole by making the multi-selection box a solid hit target that consumes presses aimed beneath it. tldraw turns an accel-drag on a shape into a band; Excalidraw refuses to drag under it. Both exist because on a dense board the thing under your pointer is usually not the thing you want to grab. ADR 0022 rejected it *only* because Ctrl had the stronger claimant here — so if snapping ends up wanting a different key, this is next in line.

One trap that binds whichever of these takes Ctrl: **Ctrl+click is the macOS secondary click.** `DiagramCanvas.razor.js` uses `(event.ctrlKey || event.metaKey)` throughout, which is correct for keyboard shortcuts and wrong for a pointer modifier — a pointer-path platform check is needed, the same shape of split ADR 0018 already made for its two target predicates. Note also that ADR 0019 gives Ctrl+wheel a zoom meaning on the trackpad profile, and ticket 03 flagged Excalidraw's five-way overloading of Ctrl as "a warning, not a template".

Whatever this lands on, [Latched-versus-live modifier semantics](29-latched-versus-live-modifiers.md) then decides per modifier whether it is read once at press or live on every move.

## Answer

Recorded as **ADR 0024**. Prototype on `prototype/snap-guides` (`5c68479`).

**The ticket's own framing of its hardest question was already dead.** It states that screen pixels and board units "genuinely conflict" for the tolerance. Ticket 03's teardown had settled it before this ticket was worked: tldraw and Excalidraw arrived at **8 screen pixels independently**, both dividing by zoom in one place, and the reason is the same one already governing the drag threshold and hit-region sizing — the number states how precisely a human can aim a pointer, which is a screen-space fact about a hand and not a document-space fact about a board. Three more of this ticket's open questions came pre-answered from the same source: equal-spacing is table stakes rather than exotic, gap snaps are translate-only, and no reference tool shows a numeric readout.

**Two toggles at opposite defaults, resolving per axis.** `SnapToGrid` flips **on**, object snapping arrives **off**, both bindable, neither writing the other. The default flip **amends one word of ADR 0011 and costs it none of its reasoning** — that ADR says "off-by-default" and then never defends it, with all ten of its rejected alternatives about persistence, granularity and exposure. ADR 0011 stays settled; this is the map's own summary-versus-decision lesson running backwards, where the rule stated something its argument never supported. Mutual exclusion between the two toggles was rejected on an **API** argument rather than a behavioural one: both are bindable parameters, so flipping one would fire *the other's* changed callback, giving a host a write it never asked for from a chord it may have disabled. Per-axis precedence over whole-position because alignment is an axis-wise fact, and because whole-position has an unstable edge where a single-axis match dropping out produces a two-axis correction.

**Ctrl suppresses rather than inverts, and this is a real divergence from both open-source tools with a stated reason.** Inversion is coherent with *one* snap mode. With two at opposite defaults it takes the default user from grid-on/object-off to grid-off/object-**on**, handing them guides they never enabled at the exact moment they asked to be freed; inverting the aggregate instead needs a special case for both-off, at which point Ctrl stops being one sentence. Suppression is also the only direction that can never *summon* chrome. Cost recorded rather than buried: a user with both toggles off has no momentary-snap route, where the reference tools would give one.

**The macOS finding reorders the whole modifier question and closes a hole ADR 0022 did not know it had.** Ctrl+click is the system secondary click there, so a **platform check** makes a Ctrl+primary press a secondary press. ADR 0022 had already flagged that a press-time Ctrl would need this; what nobody noticed is that its own `contextmenu` suppression plus a button-2 menu means **on macOS today a Ctrl+click opens no menu at all** — native suppressed, ours never fires, and only a two-finger tap escapes it. Taking the key fixes that as a side effect. The consequence is the valuable part: **Ctrl must be read live on every move, never latched**, because on macOS a Ctrl press is not a primary press at all, so there is nothing to latch. That hands [Latched-versus-live modifier semantics](29-latched-versus-live-modifiers.md) a *derived* answer rather than a free choice, and dissolves its channel worry for this modifier, since snapping has no observable effect until the pointer moves — modifier state on `OnPointerMoved` suffices and ADR 0018 needs no new channel. It also leaves [Reaching a buried instance](37-reaching-a-buried-instance.md) with an answer harsher than "spent": Ctrl is **unusable at press time**, since a modifier working at press on Windows and not macOS is worse than none, which tilts that ticket toward the menu route it currently treats as expensive.

**Axis-lock taken, on Shift, moves only.** It was never an agreed feature — ADR 0022 has it in its *rejected* list, rejected procedurally so the constrain vocabulary could be decided in one place. The locked axis is **exempt from all snapping**, since rounding it to a grid line would move the selection along the axis just locked; that composes with per-axis precedence with no new rule, the lock removing an axis from play. **Shift stays deliberately unbound on resize**: this map ruled aspect-lock out of scope, which frees the key, and spending it would be worse than leaving it idle because Shift on a resize means preserve-aspect-ratio in every tool a user has met.

**Nine anchor pairings per axis, mover is the selection box** (ADR 0020's rigid body, no branch on selection size). Candidates come from the existing viewport query, which the ticket framed as a performance concession and is better read as **semantics** — a guide to an off-screen object is a line to nowhere, and the performance is the side effect. **Locked entities are candidates** (snapping is reference, not participation, so ADR 0017 is untouched, and locked background frames are exactly what people align to); LOD placeholders are; edges and floating endpoints are not. **Groups are excluded, and the cost is exactly one anchor** — a group's bounds are the union of its members', so every one of its four edges already coincides with some member's by construction, leaving only its *centre* as new, which sits where nothing is drawn.

**The performance claim made mid-grilling was wrong and is corrected here.** Perpendicular overlap was described as what "keeps the pair search from being quadratic". It is a *filter*, not a bound: enumerating all candidate pairs and then filtering is O(n²) per frame and breaks ADR 0020's structural budget. The order that actually fixes it is to **filter candidates to those overlapping the mover first, which is linear, then enumerate pairs only within that set** — few entities share a row with the mover on a real board. Point snapping was never at risk.

**Two implementation traps banked from ticket 03, both unreachable by reading the output.** The snap search runs **twice** per move, the second pass from the already-snapped position, or the guide describes where the selection *was*. And snapping is skipped above a pointer velocity, because it is help for someone being careful and an obstacle to someone who is not — which needs a velocity signal ADR 0018 does not currently produce.

**Scope by gesture:** resize gets point snaps only; edge endpoints go to [Edge attachment without a named port](19-edge-attachment-without-named-port.md), the reference bar treating attachment as a separate mechanism rather than a case of this one (tldraw gives it a wholly different distance formula); align and distribute untouched; keyboard nudge to [Keyboard parity for new gestures](16-keyboard-parity-for-new-gestures.md); **placement and paste get grid only**, on a mechanical boundary rather than a preference — neither is one of ADR 0018's eight pointer gestures, so neither has a preview for a guide to live in, and object snapping with no guide is a silent correction that is worse than none.

**Full-bleed guide lines won the prototype**, beating the extremes-with-crosses rendering both open-source tools draw. **That choice sets the colour rather than taste doing it**: a viewport-length line puts several times more coloured pixels on screen than one stopping at the outermost match, which is *why* the reference tools can afford saturated red, so ours runs at half intensity. New theme token, deliberately **not the accent**, since guides only appear while a selection is dragged and would vanish against the selection's own box. No numeric readout.

**One prototype finding changes an assumption made while grilling:** SVG's `vector-effect="non-scaling-stroke"` gives screen-constant stroke *thickness* under the canvas transform for free, so a guide line needs no `calc(1px / var(--d12-scale))`. It does nothing for glyph *size*, so gap caps still divide by scale. A second finding was a bug in the prototype worth not repeating: a run of equal gaps is a set of **parallel** gaps at different perpendicular positions, not a collinear chain, so tldraw's shared-midpoint rendering stacks two genuine gaps on the same pixels — each span draws at its own midpoint.

**Menu row, no chord.** Ctrl already serves the mid-task case better than a toggle could, leaving the toggle a set-and-forget preference that needs to be reachable rather than fast, and the chord budget is about to get tight. Declining it also drops a matching host-disable flag, so the API grows by one bindable pair rather than two plus a guard.

Numbers judged in the prototype: tolerance **8** screen px, sticky to **1.75x** tolerance, velocity cutoff **3** screen px/ms, guide intensity **0.5**.

Amends **ADR 0011** (one word), **ADR 0022** (macOS platform check; `Shift` gains an in-gesture meaning) and **ADR 0018** (JS reports modifiers per move plus a velocity). Confirms **ADR 0020** throughout. Satisfies **ADR 0012** by adding a token rather than amending it. **ADR 0014** keeps every rule, but the distribute drift it priced as a minority case is now the default case. Added `Object snapping`, `Alignment guide`, `Equal-spacing snap` and `Axis lock` to `CONTEXT.md`, and amended `Snap-to-grid`, `Theme token` and `Pointer gesture`.

**Unblocks [Reaching a buried instance](37-reaching-a-buried-instance.md)**, with an empty modifier budget. Surfaced [Which point of a selection grid snapping anchors](40-grid-snap-anchor.md).
