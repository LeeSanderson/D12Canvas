# Context menu enrichment

Type: grilling
Status: resolved
Blocked by: 07, 09

## Question

Decide the full action set the right-click menu offers, and in which contexts it appears.

The seed note asks for actions via a right-click menu — group/ungroup when several items are selected, duplicate, delete. Roughly half of that exists already: `SelectionContextMenu` is built, themed, keyboard-navigable, and wired into `DiagramCanvas`, offering Delete, conditional Group and Ungroup, and the four z-order commands. Duplicate is absent because no duplication model existed (ticket 09), and the menu never appears on empty canvas because `HandleContextMenu` returns early when nothing is selected, deliberately letting the browser's native menu through.

Decide:

- The action set, now that clipboard and duplication (09) have a model to draw on: cut, copy, paste, duplicate, select-all.
- Whether an empty-canvas menu exists, and what it holds — paste and select-all are the obvious candidates, and both only make sense after 09. This also settles whether the browser's native menu should ever be reachable inside the canvas. **ADR 0015 has since retired the premise that blocked this**: ADR 0009 justified having no empty-canvas menu on the grounds that no decided action belonged there, and the viewport commands (plus ADR 0011's snap-to-grid toggle) now do. So the actions exist and are waiting; this ticket decides whether they appear and alongside what. Note the asymmetry it introduces — zoom-to-fit is meaningful on empty canvas *and* on a selection, whereas paste and select-all are empty-canvas-flavoured, so a viewport section may belong in both menus rather than only the empty one.
- Whether align and distribute (12) appear here, and how a menu with two conditional sections and a growing list stays readable. Submenus, grouping, or a hard cap.
- Context sensitivity: a single instance, a multi-selection, a `Group`, a selected edge, and empty canvas are five distinct cases with different applicable actions. Today's conditional rendering handles two.
- Whether menu items surface their keyboard shortcuts, which requires the shortcut table from 09 and 16 to be settled first.
- How this composes with the selection-anchored property bar (08). Both are popovers anchored near the selection; decide whether they can be open simultaneously, and which owns dismissal.
- Disclosure of unavailable actions: hidden, as Group and Ungroup are today, or shown disabled. The current pattern makes the menu's height jump between selections.

Ticket 07 owns the *trigger* — the press semantics that decide when a right-button gesture opens this menu rather than panning. This ticket owns only what the menu contains.

## Answer

Recorded as **ADR 0023**, with a `Context menu` term added to `CONTEXT.md` and `Paste anchor` widened.

**One component handed a computed menu context, two content sets split on whether the press resolved to an entity, and rows composed by per-item eligibility** rather than a layout per context. That is what makes the five contexts the ticket named, plus the sixth ADR 0022 quietly added (a locked entity, reachable only by a secondary press), fall out of predicates the rows already need rather than six hand-written menus. Object menu: Cut, Copy, Paste, Duplicate │ Delete │ Group, Ungroup │ the align strip then four flat z-order rows │ Lock or Unlock │ Zoom to Selection. Canvas menu: Paste │ Select All │ Zoom to Fit, Zoom to 100% │ Snap to Grid │ Unlock All. Every row is an action a prior ADR decided, with **Unlock All the single exception** and it introduces no command type. Section order is fixed and **a separator renders only with a rendered section on both sides**, which is a decision rather than detail because the sparse contexts are exactly where naive separators look worst.

**The clipboard rows cannot use ADR 0013's mechanism, and finding that out was the most valuable thing this ticket did.** ADR 0013 routes cut/copy/paste through the DOM clipboard events *because* the `paste` event is the only permission-free read path, which is correct and keyboard-only by construction: a click on a row fires no clipboard event and nothing can synthesise one. Probed in a real browser rather than reasoned about, since Playwright grants `clipboard-read` at the context level and would have hidden the one behaviour that mattered. Three facts came back. A button click fires nothing, with `Ctrl+V` as the control, so the split is forced rather than chosen. **User activation survives the Blazor interop hop and a deliberate two-second delay on top of it** — the fact most likely to have killed the approach, because a menu row's payload is known in C# so the write cannot happen inside the native handler, and had activation expired the row would have worked on WebAssembly and failed silently in a Blazor Server host, which no test in this repo would catch. And Chromium prompts once per origin and remembers. So **ADR 0013's mechanism becomes per-surface**: keydown keeps the events, the menu uses `navigator.clipboard.read`/`write`, `read` rather than `readText` so a foreign bitmap still arrives. Residual cost stated rather than glossed: the async API is absent outside a secure context, so a host on plain HTTP keeps the keyboard route and loses the menu's clipboard rows. **The paste anchor gains a third case** for the same reason — the pointer is over the menu by the time a row is clicked, so ADR 0013 read literally sends a menu paste to the viewport centre; it anchors at the press point ADR 0022 already stores, and the rule generalises to "where the user last indicated" rather than gaining an exception.

**Readability is answered by a strip, not the submenu or cap ADR 0014 anticipated.** The eight align and distribute actions render as one horizontal row of glyph buttons, `role="group"` of `menuitem`s labelled by `title`. Four arguments, of which the second is the one that decides it: no reference tool renders "Align left" as a word; **ADR 0014's 2-and-3 thresholds become a width change instead of the menu growing and shrinking by eight rows**, which was the height-jump cost the ticket raised under disclosure; ADR 0021 already established that a glyph beats a word for something judged by eye; and the keyboard cost is Left/Right within the strip versus a submenu's hover timing, second popover, and a rewrite of `focusAdjacentItem`. **The four z-order rows stay flat** — burying already-shipped high-frequency behaviour one hover deeper is a regression users feel. Eleven rows for a single instance, thirteen for a multi-selection.

**The menu flips rather than clamping, and that fixes a live defect.** `MenuStyle` has no bounds check and `.diagram-container` declares `overflow: hidden`, so a right-click near an edge cuts items off unreachably *today*. ADR 0021 told this ticket to adopt its clamp; the divergence is licensed by ADR 0021's own three arguments, **all of which describe a persistent surface that re-anchors** — no boundary to oscillate across for something placed once and dead on the next press. Plus a cost the bar never pays: clamping slides a menu back over the pointer, putting a row under the cursor. Two surfaces, two placement rules, and the difference is persistence rather than taste.

**Disclosure follows precedent (hidden, per ADR 0014 and 0015) and hints are refused outright.** ADR 0014's eight chords, lock, unlock-all and the keyboard route to the menu are all undecided, so hinting only the settled rows ships a menu where some rows explain themselves and others silently do not. Handed to ticket 16 with two things attached: any binding it decides has to reach the menu, and a hint is the first thing in the library that must *render* a platform-dependent string, which is a second consumer of the platform fact ADR 0022 already needed.

**The dismissing press is consumed, in the capture phase, and only inside `.diagram-container`.** Capture is what keeps **ADR 0018 entirely untouched** — the press never reaches the arbitration listener, so none of its synchronous role-derived decisions learns that a menu exists. Container-scoping is the embeddable-library half: swallowing every outside press matches the platform contract exactly and makes the library eat presses on the host's own Save button, which is a bug report the host cannot diagnose. ADR 0002 already draws that line. Accepted cost: with pan on the secondary button, right-dragging while a menu is open dismisses instead of panning.

**The sharpest find was that ADR 0022 wrote its `author-content` rule against the role when its reasoning is about editable content.** Built-ins classify as `author-content`, so as written **a right-click on a sticky note's body gets the browser's menu, not the object menu** — the most common object on a whiteboard, defending a spellcheck menu with nothing to check. Narrowed to `Native` only when the target is editable or a text selection is live, which amends one cell of ADR 0022's table and needs no new mechanism, ADR 0018's predicate already existing. The handle route was rejected explicitly rather than overlooked: it works, and nobody discovers it.

Two smaller things. **A mixed locked-and-unlocked selection is unreachable** under ADR 0017 plus ADR 0022, so Lock/Unlock needs no third state, which is worth knowing before someone designs one. And **`OnToggleSnapToGridPressed`'s guard is in the wrong place**: `EnableSnapToGridShortcut` disables a chord, so it moves to the keydown call site, which also fixes a host calling that public method directly and getting silently nothing.

**Handed back rather than decided: Figma's `Select layer` z-order submenu**, which the reference-tool teardown assigned here by name. It needs `elementsFromPoint` plumbing, a highlight affordance reaching from a row onto board content, a decision about whether an instance has an identity a user can read (`DisplayName` is on the registration, so three overlapping rectangles give three rows reading "Rectangle"), and the submenu machinery this ticket rejected. ADR 0022 meanwhile has press-through-with-a-modifier as the cheap route to the same hole, askable once Ctrl is settled. Two candidates for one question belong in one decision. One finding banked on the way out: **ADR 0017's rejection of a C#-side ranked hit list does not rule out exposing a stack**, because `document.elementsFromPoint` gives paint order from the same authority that classified the press.

Amends ADR 0013 (twice), ADR 0022 (one cell), and ADR 0017 (an unlock item plus one new action). Discharges the deferrals in ADR 0014 and ADR 0015 and fills in the contents ADR 0009's paragraph was left waiting for. Diverges from ADR 0021 once, deliberately. Confirms ADR 0002 and ADR 0018 untouched.
