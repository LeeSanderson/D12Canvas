# Edge visibility and board-content theming

Type: grilling
Status: resolved

## Question

Decide how edges get their colour — and, behind that, whether board content has any theming story at all.

The seed note reports connectors being hard to see against dark backgrounds. The immediate cause is plain: `.edge-line` in `DiagramCanvas.razor` is `stroke: #4a4a4a`, a hard-coded mid-grey that never joined the token layer. Ticket 74 of `d12canvas-next` swept the remaining chrome into `--d12-*` tokens and did not touch edges.

The reason it did not is the actual question. ADR 0012 draws a hard line: theme tokens style *library-owned chrome*, while per-instance visual fields are ordinary `TProps` business data with no separate theming model. `CONTEXT.md` restates it as an explicit "avoid". An `Edge` is board content — a persisted entity in `Board.Edges` — so by that rule it should carry its own colour as data, not read a token. But its colour has never been exposed as data either, so it currently gets neither.

Decide:

- Which side of ADR 0012's line an edge falls on. It is board content that is nonetheless rendered entirely by library chrome, with no author-supplied component behind it — genuinely unlike both a sticky note and the grid.
- If tokens: how a user-set per-edge colour would coexist with a themed default later, without ADR 0012 having to be reopened a second time.
- If data: where the colour lives on `Edge`, how it defaults, how it round-trips through ADR 0004's envelope, whether it is panel-editable, and what happens to boards already persisted without it.
- **The wider problem this exposes.** The same argument applies to every built-in component type. A sticky note's yellow, a rectangle's fill, a text component's colour are all `TProps` fields with light-mode-shaped defaults (ticket 10 of `d12canvas-next` put visual fields in props deliberately). On a dark theme they are all wrong, not just edges. Decide whether that is in scope here, a separate ticket, or an accepted consequence of ADR 0012 that this effort records and leaves.
- Whether selected-edge and arrowhead colours, and the `--d12-connector-preview` escape hatch that ticket 74 already created for the drag preview, come out consistent with whatever is chosen.
- Contrast as a requirement rather than an aesthetic: whatever is decided should state how an edge stays legible against an arbitrary user-chosen component fill, which is not a theme problem at all.

## Answer

Recorded as **ADR 0016**. `CONTEXT.md`'s `Theme token` entry widened and a new `Edge colour` term added; ADR 0012 gained an "extended by 0016" pointer but stays **settled** — nothing in it is reversed, so this is not ticket 09's reopening move.

**The framing was wrong, and fixing it was the decision.** The ticket asks which side of ADR 0012's chrome-versus-content line an edge falls on. It falls on neither, which is exactly why it ended up with no token *and* no data field. The real line is **who renders the pixels**: a sticky note's yellow is untouchable because an author's component paints it; an edge has no author component, so the library may supply its default. ADR 0012 never said "only chrome may read tokens" — the case simply did not exist. So the token layer gains its **first content-role token**, which is deliberately *not* the `--d12-connector-preview` case (that is 0012's escape hatch, a divergence from a token an element could have read; this is a new role).

**Data with a token-resolved default.** `Color` joins `EdgeStyle` — the existing before/after snapshot behind `ChangeEdgeStyleCommand` — so **no new command type** and undo is free, matching ADR 0014's and ADR 0013's precedent. A CSS colour `string`, consistent with every built-in colour prop rather than a bespoke value type; **nullability is the one divergence and is load-bearing** (`null` = no author opinion), empty normalising to null. Persistence is one optional envelope parameter, **no `SchemaVersion` bump** — an old board deserialises to `null` and therefore renders *more* correctly than when it was saved, so nothing migrates.

**The cascade does the fallback, not the C#.** Both obvious routes are silently broken: a presentation attribute sits at the bottom of the cascade so CSS would override the author's colour, and an inline `stroke` beats `.edge-line.selected` so selection would fail to recolour. Instead `stroke: var(--d12-edge-override, var(--d12-edge))`, with `--d12-edge-override` rebound inline only when `Color` is set. The renderer never learns selection exists — it answers one question, and `.edge-line.selected` wins on specificity because it sets a *different declaration*. "Null falls through to the token" becomes literally the cascade's fallback. The override is a **separate property from the token**, not a rebinding of `--d12-edge`, so board data never writes into a theme token on the first use of the boundary this ticket draws.

**The trap that would have shipped: `<marker>` content does not inherit the referencing element's stroke.** Arrowhead defs are shared across all edges and coloured by a class *inside* the def, so per-edge colour would have produced coloured lines with grey arrowheads, unfixable by any CSS on the referencing element. `fill="context-stroke"` resolves the marker's fill from the referencing element's stroke — legal (both keywords are paint values), universal (Firefox 111 Mar 2023, Chrome 124 Apr 2024 as the binding floor, WebKit earlier), and it **deletes a def rather than adding one**: `edge-arrow-selected` exists only to carry a different fill, so it becomes redundant and `EdgeMarkerUrl` loses its `isSelected` parameter. Cost: arrowhead colour leaves CSS entirely, so `.edge-arrowhead`'s fill rule vanishes and nothing is left to grab by class.

**Selection is always the accent**, overriding the edge's own colour — ADR 0006 makes selection transient unpersisted UI state, which puts it on the library's side of the new line. This is the status quo tokenised (`#2f80ed` already equals `--d12-accent`), so no light baseline moves. Known limit kept rather than solved: an author who picks the accent blue gets no colour change on selection, and the 2→3 `stroke-width` bump is retained explicitly as the non-colour cue.

**Contrast is a guarantee about the token pair only** — `--d12-edge` ≥3:1 against `--d12-surface` in both themes (light above 7:1, dark above 6:1), testable rather than eyeballed. Light is **byte-for-byte the existing `#4a4a4a`**, so the visual-test diff is confined to the dark cases that are currently broken. **No guarantee attaches to an authored colour** — ADR 0008's position on a component's own fill, applied consistently. Bullet 6's "arbitrary user-chosen component fill" largely **dissolves on paint order**: `.edges-layer` is `z-index: 0` and containers carry `z-index: {ZIndex}` from `NextZIndex()`, siblings under the transformed `.canvas-content`, so edges paint *beneath* components and are occluded rather than crossing them.

**No editing surface ships.** Not a gap this creates — `RoutingStyle`/`SourceArrow`/`TargetArrow` are *already* settable behind a commit point commented "No panel UI calls this yet", so colour becomes the **fourth property behind one missing surface**, fixed by one surface. Handed to [Selection-anchored property bar](08-selection-anchored-property-bar.md) with a structural finding: `PropertyPanel` cannot represent an edge at all — every `PanelField` target is a `(ComponentInstance, PropertyInfo)` pair discovered via `ComponentTypeKey` → registry → reflected `TProps`, and an `Edge` has neither, so `[PanelEditable]` cannot simply be applied. The discovery path is closed to entities, not missing a case.

**Scope folded in (binding on implementation): ticket 74 of `d12canvas-next` did not in fact sweep all remaining chrome.** Still hard-coded in the same `<style>` block: `.selection-bounding-box` (`#2f80ed`), `.drag-over-affordance` (`#4a90d9` — a *third* blue, matching nothing), `.floating-endpoint` (`#f39c12`/`#ffffff`). The bounding box is the instructive one: byte-identical to the accent so it looks right today, while `.marquee-select` directly above it reads the token — so **a host retuning `--d12-accent` desynchronises the marquee from the bounding box**, a latent bug invisible until the contract is used as designed. Folded in because the standing rule triggers a full Playwright run on any edit to this shared block, so doing them separately pays that cost twice for a find-and-replace.

Surfaced [Themed visual defaults for built-in component types](25-built-in-themed-defaults.md). Two findings handed on: **send-to-back can push a component beneath the edges layer** (`PreviousZIndex()` goes negative while `.edges-layer` is pinned at 0, producing the one case the contrast reasoning excludes — ADR 0008's question, not this one's), and **built-ins freeze light-mode assumptions into board data at placement time**, which is what the new ticket exists for.
