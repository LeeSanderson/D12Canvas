# Port affordance model

Type: prototype
Status: resolved
Blocked by: 01, 19

## Question

Decide when a component instance's ports are visible, and where they sit relative to the resize handles — currently the two collide both in trigger and in geometry.

Two seed notes land here. Ports appear on hover, which the reported experience says is wrong: they should appear while a connector is being dragged, or when the instance has focus. And the resize handles overlap the ports badly enough to make resizing difficult.

The geometry collision is exact, not approximate. In `ComponentContainer.razor`'s style block, `.port-top` is a 20px circle at `top: -10px; left: calc(50% - 10px)`, and the `.top` resize handle is a 10px circle at `top: -5px; left: calc(50% - 5px)` — perfectly concentric. Ports render before the resize handles in markup, so the handles win the stacking tie-break and sit on top of the ports at all four border centres. Visibility is CSS-only today (`.component-container:hover .port, .component-container.selected .port`), with no C# state involved — a property worth keeping if the new model allows it.

Build a prototype and decide:

- The visibility trigger. Focus, active connector drag, proximity, a modifier key, or some combination — and what happens for a *target* instance during a drag originating elsewhere, which is when ports matter most and when the source instance's own hover state is irrelevant.
- The geometry. Move ports outboard of the handles, move handles inboard, offset them along the edge, or change what appears at border centres versus corners. Whichever way, resize must stay reachable at every border midpoint.
- Hit-target sizing under zoom. Ports and handles are fixed CSS pixel sizes inside a scaled container, so at low zoom they shrink toward unusable and at high zoom they bloat over the content. ADR 0011 made zoom unbounded, which sharpens this considerably.
- Interaction with the port strips. Double-clicking a border strip adds a custom port (`.port-strip`, 14px wide, straddling the border) — it must not become unreachable, and must not fire when the user meant to resize.
- Whether custom ports, which sit at arbitrary fractional positions, can collide with handles the same way and need the same treatment.
- Whether any of this survives the touch non-foreclosure constraint, given hover has no touch equivalent.

Amends ADR 0005, which specified the four standard ports but not their affordance.

**Constraint from ADR 0026 (ticket 16 resolved):** the keyboard-parity work could not answer what this decision means for keyboard users, because this ticket still changes what affordances exist. What it hands over is a constraint rather than a preference: **ports must be reachable and visible without hover.** ADR 0010's mouse-free connector attachment already depends on it, and the code is live rather than planned — `Enter` enters port picking, arrows jump to the four standard ports, `Space` reaches a custom one. If ports become visible on focus rather than on hover, record that as the accessibility improvement it is; if they stay hover-dependent, this ticket owes an explanation of how a keyboard user aims.

Separately, ADR 0025's relationship test handed this ticket `PortHitRadius = 10`, which is board space by its own comment and therefore cannot join the screen-pixel ordering. ADR 0026 adds one more member to that ordering worth checking against: the grid nudge step, whose dominant cell is 6.3 to 63 screen pixels.

**Constraint from ADR 0027 (ticket 19 resolved, unblocking this one):** the visibility trigger is no longer only about discoverability. A connector drop now resolves in three zones — a port's hit radius pins the endpoint, anywhere else over a component produces an `Auto endpoint`, nothing floats — and ADR 0017's rule that affordances leave the render set and the hit set together therefore means **wherever a port is not visible, an edge cannot be pinned there at all, only auto-attached**. So this ticket's visibility decision is also a decision about where each of the two attachment kinds is reachable, and the two obvious answers differ in kind rather than degree: ports rendered during any live connector drag makes pinning available on every plausible target, while ports rendered on hover or focus only makes pinning available on whatever the pointer has already visited. Neither is wrong, but the consequence should be chosen rather than inherited.

Two things get easier. `PortHitRadius` becomes `N / scale` with **`N` owned by C# and published through `ContentStyle`** exactly as `--d12-scale` is, because ADR 0027 resolves the drop geometrically in C# against `Board` and a number defined in both CSS and C# would drift — so this ticket picks one number with one owner rather than reconciling two. And the concentric port/resize-handle collision is already settled *for the connector drop* without waiting on the geometry here, since a C#-side resolver never sees resize handles and proximity to the port decides. The collision at press time is untouched and still this ticket's.

One thing was handed back rather than solved: ADR 0027 found that a single drag can only produce auto at the **target**, because `StartPortDrag` begins from a port and a drag from an instance body is ADR 0018's `MoveSelection`. Auto at the source needs a second gesture today. **Whether a connector drag should be startable without naming a port** — Miro pulls from a hovered shape's border rather than from a dot — belongs here, since it is a question about what affordance exists.

## Answer

**A side is partitioned along its length, ports appear on selection and on the drop target, and the cursor is the only thing that draws the partition.** Recorded as ADR 0028.

The ticket's own written constraint — *"resize must stay reachable at every border midpoint"* — was tested first, because it rules out the only answer any reference tool actually ships. Read as *resize must stay reachable along every side* rather than at the exact centre pixel, it survives and buys a better option than Miro's: the side's **run** (its length minus a corner reserve at each end) partitions into a port span in the middle and resize spans out to the corners. **Miro's layout then falls out as the small-shape case** — shorten a side until it holds one span and every side is entirely port with resize at the corners — rather than being written as the rule, and today's stack is unreachable at any size.

**The collision is a spec failure, not an aesthetic one**, which is what makes ADR 0017's holding position (resize handle beats port, "expected to separate geometrically so this rule almost never fires") unusable as an end state. WCAG 2.2 SC 2.5.8 admits undersized targets only if a 24px circle centred on each does not intersect its neighbour's, and **concentric targets fail that at every zoom by construction**. So the precedence is **retired rather than kept as a backstop** — a backstop for a case the geometry cannot produce is a rule no test can reach — and replaced by an invariant: no two affordance regions on an instance's border intersect, at any zoom, for any port configuration.

**Visibility is selection plus the drop target, never hover.** Hover is not merely the wrong slot but an unusable one: tldraw suppresses hover affordances outright on coarse pointers, so the touch constraint kills it without any argument about taste, and ADR 0026 needed ports visible to a keyboard user who has hovered nothing. ADR 0010's focus-follows-selection collapses the seed note's two options into one trigger. Miro's *documented* trigger is selection too; its hover behaviour is `[observed]` only. During a drag only the component **under the pointer** lights up, and the consequence is chosen rather than inherited, since ADR 0027 made this a reachability decision: pinning is available only where a port is rendered, so pinning becomes a two-stage act (arrive, then aim) where auto stays one — which is the ordering ADR 0027 wanted, the easier gesture giving the more forgiving result.

**One computation per side, and it is 1-D because `AddCustomPort` pins the perpendicular fraction to the side's own 0 or 1** — so although `PortDef` is a 2-D fraction, nothing in the product can create an interior port. Every port takes the stretch of the run nearest to it, capped at the port target; two ports closer than the cap split the difference; resize takes the leftovers; anything below the floor drops from render and hit together, which is ADR 0017's rule applied with no port-specific exception. **Ports win and resize is residual**, so a user can bury their own side-resize affordance by adding ports, with zoom the only recovery and nothing on screen explaining it. Corner resize is the one thing that can never be covered, protected **structurally** (the reserve is subtracted before any port is placed) rather than by a precedence.

The numbers collapse to **one**: `N` = 24 screen pixels, WCAG's minimum, defined in C# and published through `ContentStyle` as ADR 0027 already requires. Floor = `N/2`, corner reserve = `N`, corner hit target = `N`. `PortHitRadius = 10` **board units** dies. Visuals keep today's sizes (20px dot, 10px handle) and **clamp below 0.25× while their targets do not**, taking the split ADR 0017 deferred here. Two findings fall out. **ADR 0026's nudge step cannot join the screen-pixel ordering** — 6.3 to 63 screen pixels is a range straddling every member of it, which is a property of that decision rather than a gap. And **the affordance floor always bites before `LodSizeThreshold`** (a default 200×140 instance loses its last port at ~0.34×, LOD swaps at 0.16×), so an `LOD placeholder` is never asked whether it has ports and ADR 0011 is confirmed without a clause.

A cap of `N` with a floor of `N/2` has one bad edge the prototype made visible: two ports closer than `N` both drop, **including the standard one**, so adding a custom port near a midpoint would delete the port `Auto endpoint` resolves to and the arrow-key pick lands on first. **The standard port keeps its full `N` and the custom port is clipped** — a precedence justified by what the two are, and the same move tldraw writes down for its own overlapping handles.

**The partition is never drawn.** Three variants were prototyped (dots only; segments always; dots at rest with segments on the drop target) and dots-only won, which makes the **cursor** load-bearing rather than fog: `crosshair` on a port span, `ns-/ew-resize` on a resize span, corner cursors on corners, `move` on the body. It is free, because ADR 0017 already makes every hit region a real element, so this adds nothing to ADR 0018's five synchronous role-derived decisions. The prototype earned two findings by hitting the walls. **Side resize loses its drawn handle entirely** — nothing on a selected shape says a side is resizable — which is precedented (Figma and tldraw both use invisible edge zones plus a cursor) and is exactly why the cursor cannot stay deferred. And the cursor turns out to **draw the partition only where the user is looking**, teaching the boundary without putting it on screen, which none of the drawn variants can do.

**Adding a custom port loses its hint and gains a menu row.** One element gets one cursor and the drag meaning wins, so `.port-strip`'s `cursor: copy` goes. The double-click itself is *better* off: ADR 0018's press-count dispatch plus a threshold that never promotes a stationary press means a dblclick and a drag share the span unambiguously, where today the strip is reachable only where neither the port nor the handle covers it. An **Add port here** row joins the object menu, eligible only when the opening press landed on a border span, costing one predicate (ADR 0023's per-item eligibility) and one stored press point (ADR 0022) and **no new command type**. That row is **pointer-only by construction**, which exposed a gap this ticket found rather than made: `AddCustomPort` has exactly one caller and neither ADR 0010 nor ADR 0026 mentions adding a port, so **a keyboard user cannot add a custom port by any route** — split out as [Keyboard route to adding a custom port](43-keyboard-add-custom-port.md).

**ADR 0027's handed-back question is answered by the partition rather than by a new gesture.** A connector starts from the *side*, because a port's hit region is a stretch of border and the dot is never aimed at — Miro's pull-from-the-border, with the source still always a named standard port, so ADR 0027's "auto at the source needs a second gesture" survives and `PortRef` needs no third case. A body drag stays `MoveSelection`; no modifier is available to change it anyway (ADR 0024 spent `Ctrl` and `Shift`, `Alt` is reserved).

**Touch needs nothing built, and no touch case is written anywhere.** `N` reads from `pointerType`, which ADR 0017's classification already carries; only the mouse value exists. Switching the resize spans off (Excalidraw's `canResizeFromSides` is false on phones) makes every side entirely port, which is Miro's layout — the same rule with one input changed.

One finding handed on rather than fixed: **`CONTEXT.md`'s "small closed set" of commands listed eleven and omitted five that exist** (`AddCustomPortCommand`, `AddEdgeCommand`, `RemoveEdgeCommand`, `NudgeCommand`, `ResizeStepCommand`). The enumeration is corrected; whether the set is still meaningfully closed, and whether "not one bespoke class per gesture type" still describes the code, is left open rather than answered in passing.

Recorded as **ADR 0028**, amending 0005, 0017 and 0023, confirming 0011, 0018, 0026 and 0027, with `Border partition` added to `CONTEXT.md` and `Port`, `Hit region`, `Context menu` and `Command` widened or corrected. Prototype on `prototype/port-affordance` (`cec3e84`), route `/port-affordance-prototype`, with every constant exposed as a slider against a live zoom.
