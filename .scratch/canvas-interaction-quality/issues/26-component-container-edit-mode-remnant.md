# What remains of ComponentContainer's edit mode

Type: grilling
Status: resolved

## Question

Decide what `ComponentContainer`'s edit mode is for, once ADR 0018 has taken every gesture off it.

ADR 0018 makes the canvas the sole owner of pointer gestures and deletes the `_editMode`-gated `_isDragging`/`_isResizing` pair — a second, parallel drag/resize implementation that predates the Board-backed canvas and is reachable only from `/componentcontainer-demo`. But `_editMode` does not die with it. It still gates `ShowSelectionOverlay => (IsSelected && !IsMultiSelected) || _editMode`, still drives the `edit-mode`/`view-mode` class pair on the container root, still has a public `InitialEditMode` parameter, and still rides in `ComponentContainerStateChangedEventArgs.IsEditMode`.

So the concept survives as a *rendering* mode with no gestures behind it, which is either a legitimate standalone-usage feature or a vestige — and it is currently impossible to tell from the code which.

Decide:

- **Whether edit mode is a concept the library keeps at all.** If a container's selection overlay is already governed by `IsSelected`, what does `_editMode` add beyond a second route to the same visuals? Note ADR 0017 made affordance rendering and hit participation one predicate; a mode that shows affordances without a gesture behind them would violate the spirit of that, since an overlay you can see but whose handles do nothing is worse than no overlay.
- **What `/componentcontainer-demo` is demonstrating.** It is nav-linked and has no visual-test coverage of its own, so nothing currently pins its behaviour. If a standalone container outside a `Board` is a supported usage, it needs a stated contract and a test; if it is not, the page and the parameter go.
- **Whether `InitialEditMode` and `ComponentContainerStateChangedEventArgs.IsEditMode` are public API a host may be relying on**, and what removing them costs. `D12Canvas` has no released-version story recorded, which makes this cheaper than it looks — confirm that rather than assume it.
- **What happens to the `edit-mode`/`view-mode` CSS class pair**, which is the piece most likely to move visual-test baselines. Any change here touches rendered markup and a shared `<style>` block, so `AGENTS.md`'s full Playwright run in the pinned image applies.

This is deliberately not part of ADR 0018's implementation scope: deleting the gesture pair is mechanical and follows from the ADR, while deciding whether a *mode* survives is a separate call with its own public-API consequences.

## Answer

**Edit mode is deleted entirely, and a container gets one rendering governed by `Selection`.** `_editMode`, `InitialEditMode`, `SwitchToEditMode`, `ExitEditMode`, the `[JSInvokable] OnClickOutside` entry and the `registerClickOutside`/`unregisterClickOutside` JS pair all go; `ShowSelectionOverlay` becomes `IsSelected && !IsMultiSelected`. The ticket asked whether the surviving concept is a feature or a vestige and said it was impossible to tell from the code. It is tellable, and the answer is neither: **it is a feature that has never worked.**

**`InitialEditMode="true"` is a one-way door and always has been.** `OnInitialized` sets `_editMode = InitialEditMode` and never registers the dismissal listener; only `SwitchToEditMode` calls `RegisterClickOutsideHandler`. A container that starts in edit mode can never leave it, and `/componentcontainer-demo`'s first container shipped in exactly that state. **No test could have caught it, because the test that covers it supplies the missing step itself**: `ComponentContainer_ClickOutside_ExitsEditMode` sets `InitialEditMode: true` and then calls `container.Instance.OnClickOutside()` directly, which is what the listener would have invoked had it ever been attached. Green test, dead wire. That is ticket 04's shape and ADR 0026's `Ctrl+Tab` shape a third time on this map, and the tell is the same each time: the test drives the entry point the browser was supposed to reach. The listener is a module-level singleton besides, one `handler` in the module with `registerClickOutside` unregistering before it installs, so two containers in edit mode leave the first stuck the same way, reachable on the demo page with one double-click.

**ADR 0018 removes the only entry that worked.** `@ondblclick="SwitchToEditMode"` is one of the three double-click meanings 0018 names and deletes. After that the concept has no entry gesture at all and the only way in is the parameter that cannot be undone, so this is a decision not to build a mode rather than a decision to remove one.

**Keeping it would have cost a guard ADR 0018 is in the middle of deleting.** `StickyNote.razor` and `Text.razor` both carry `@ondblclick:stopPropagation` on the element that begins inline editing, for the stated purpose of stopping that double-click reaching `SwitchToEditMode`, and `DoubleClickToEnterInlineEditDoesNotAlsoEngageComponentContainersLegacyEditMode` asserts it. ADR 0018 line 123 deletes that `stopPropagation` on the ground that inline editing composes via `Native`, which is only safe if nothing above the author's content wants the double-click. So deleting the mode is what makes 0018's deletion of the workaround correct rather than merely convenient.

**Text editing was never routed through edit mode**, which is worth recording because it was the first thing asked of this ticket and the code answers it decisively in the opposite direction. `BeginEdit` flips a private `_isEditing` inside each built-in, swaps the `<p>` for a `<textarea>` and commits on blur through `ParentCanvas.CommitPropsChange` as one `MutateEntityCommand`. Nothing in that path reads `_editMode`, and the relationship between the two is not a dependency but a collision the codebase spends two `stopPropagation` directives and a test keeping apart. **The requirement is the inverse of the fear**: entering the text editor must *not* enter container edit mode.

**The demo page is deleted, nav entry included, and the usage it appeared to represent survives in a narrower form.** Everything the page demonstrated is gone: edit mode, the legacy drag and resize pair, and the JSON status readout. The ticket framed this as a binary, standalone usage is supported and needs a contract and a test, or the page and the parameter go. **There is a third answer, because the page is not the only consumer.** `VirtualizationStressTest.razor` mounts containers as `DiagramCanvas` child content with no `Board`, using `X`/`Y`/`Width`/`Height`/`@key` and child content and nothing else, and the `d12canvas-next` map kept that page deliberately as a permanent dev tool. So the usage narrows rather than dying: **a `ComponentContainer` with no enclosing entity renders as a positioned box with its child content, shows no affordances and answers no gesture.** That is not a concession but what ADRs 0017 and 0018 already force, since classification yields `(role, entityId, part)` and every content role carries an entity id, so a container that is not board content has nothing for a gesture to act on. Stated in `CONTEXT.md` and pinned by one bUnit test, since the page that used to demonstrate it is going.

**`InitialEditMode`, `OnStateChanged` and `ComponentContainerStateChangedEventArgs` all go, and the ticket was right that this is cheaper than it looks.** `OnStateChanged` has exactly two firing sites, both inside gesture branches 0018 deletes, and its only consumer was the demo page, so it could never fire again. The args class goes whole rather than losing one field: `IsEditMode` cannot outlive the mode and the other four duplicate what `OnMoved`/`OnResized` report on commit, with live geometry now ADR 0020's `LiveGeometry`. **Confirmed rather than assumed, as the ticket asked**: `D12Canvas.csproj` declares no `PackageId`, no `Version` and no `GeneratePackageOnBuild`, and `Directory.Build.props` carries only `TreatWarningsAsErrors` and the CSharpier check. No published package, no released-version story, nothing outside this repo to break.

**Both class names go and the one pixel stays.** The ticket called the class pair the piece most likely to move baselines, and it is the piece that moves none. `.view-mode` declared `border: 1px solid transparent` under `box-sizing: border-box`, so it insets every instance's content by 1px on all four sides on every board. That declaration moves onto `.component-container` unchanged, keeping rendered geometry byte-identical and leaving the nav entry as the single reason any baseline moves. Deleting the border outright was the tempting option, a value nobody chose doing invisible layout, and it was rejected for growing every instance's content by 2px in a change no ticket asked for, landing in the same 50 screenshots with no way to tell the two apart. ADR 0017 is undisturbed either way: the participating element is the border box, which is exactly `Bounds`, and the inset sits inside it.

**The real baseline cost is where the ticket did not look.** The visual suite screenshots with `FullPage = true` via `Verify(_page)`, and the nav sidebar is in every shot, so removing one nav row changes all 50 `.verified.html` files and all 50 `.png` baselines. Mechanical and uniform, but a full Playwright run in the pinned image with `-parallel none` and 50 image approvals.

**Five tests move.** `ComponentContainer_ClickOutside_ExitsEditMode` and `EditModeInstanceRendersResizeHandlesEvenWhenUnselected` go. `UnselectedInstanceOutsideEditModeOmitsResizeHandles` keeps its assertion and drops the dead clause from its name. `DoubleClickToEnterInlineEditDoesNotAlsoEngageComponentContainersLegacyEditMode` goes, its surviving half already covered by `StickyNoteTests.DoubleClickEntersEditModeRenderingATextEditorInPlaceOfTheParagraph`. **`ComponentContainer_ImportsColocatedJsModule` needs a new assertion rather than deletion**: it asserts `view-mode` today under a name about the module import, and the import is actually proved by the render not throwing under bUnit's strict JSInterop, so the name was right and the assertion was borrowed.

**`_dotNetRef` loses its only consumer** when `OnClickOutside` goes, and the `_jsModule` import and `IAsyncDisposable` survive only while `focusElement` has a caller, which is `HandleClick`, which 0018 deletes. The container may end up needing no JavaScript at all; that trigger belongs to 0018's implementation, not here.

**Handed on.** `.component-container` declares `cursor: move` unconditionally, promising movability on a `Locked` entity and on a container with no way to move at all, which goes to the cursor and micro-feedback patch and is notable there for being visible **at rest**, so ADR 0031's pointer-capture argument does not reach it. Two more hard-coded blues go to [Enumerate every hard-coded colour left in the library](47-hard-coded-colour-sweep.md): `#3498db` on `.resize-handle` and `#2f80ed` on `.selected`, a fourth and fifth beyond ticket 14's three.

Recorded as **ADR 0035**, amending 0018 in two places, confirming 0017/0020, with `Component container` added to `CONTEXT.md` and `edit mode` recorded there as retired vocabulary. No new tickets surfaced and no fog graduated.
