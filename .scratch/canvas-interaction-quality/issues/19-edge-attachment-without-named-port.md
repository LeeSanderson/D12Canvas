# Edge attachment without a named port

Type: grilling
Status: resolved

## Question

Decide whether `EdgeEndpoint` gains a case that attaches to a component *without* naming a port — letting routing pick the side — and whether `RoutingStyle` constrains which endpoints are legal.

Ticket 03 found this to be the largest single divergence between D12Canvas's settled decisions and the reference bar. None of Miro, FigJam, tldraw or Excalidraw exposes discrete ports as the primary attachment model; all four bind to a normalized anchor over the target's bounds and treat named sides as sugar over it. Every one of them has an auto/centre/imprecise state that `EdgeEndpoint` cannot currently express:

- Miro: `snapTo` (`top`/`bottom`/`left`/`right`/`auto`) and `position` (fractional) are "always in sync, and mutually exclusive" — and it surfaces the distinction as two user-visible drop targets on the same object: drop on the **body** for a connection that re-routes to the shortest path, drop on an **edge dot** for one that stays pinned.
- Figma: `ConnectorEndpoint` is a three-variant union whose magnet includes `AUTO` and `NONE`.
- tldraw: `normalizedAnchor` defaulting to the shape centre, with `isPrecise: false`.
- Excalidraw: `mode: "inside" | "orbit" | "skip"` alongside a `fixedPoint` anchor.

ADR 0005 rejected "dynamically-calculated, unnamed anchor points" — but the teardown's reading is that it rejected the wrong thing, since the reference anchors are both named *and* dynamic: "auto" is a name.

Decide:

- **Whether `EdgeEndpoint` gains an attach-to-component-without-a-port case**, and if so whether it is a third union case or a distinguished `PortId` value.
- **What the common drop gesture produces.** ADR 0009 says dragging from a port starts an edge, but the reference bar's common case is dropping on the *body* of a target with the edge dot as the precise case. `CompletePortDrag` should be read against that — dropping on a component rather than a port is the gesture that most needs to work well, and it is currently the one with no endpoint to produce.
- **Whether `RoutingStyle` and endpoint choice stay independent per-edge fields.** Every tool that models both couples them: Figma constrains magnets by line type ("Elbowed connectors may use all magnets besides CENTER. Straight connectors may use only CENTER or NONE"), Excalidraw's midpoint magnets exist only for elbow arrows, tldraw's directional handles are elbow-only. D12Canvas can express `Straight` + `PortId.Top`, which all three consider ill-formed. Either state the coupling, or decide what four ports mean for a straight edge — no reference tool has an answer for the latter.
- **Whether custom ports survive as authored entities**, given Excalidraw reached the same expressive power with a handle owned by the *arrow endpoint* rather than the shape — one per endpoint, created by binding, hidden when redundant, and costing no per-instance persisted state or affordance on every unselected shape.

Amends ADR 0005. Blocks ticket 06: the port affordance question cannot resolve cleanly while the model has no way to express "you pick".

## Answer

Recorded as **ADR 0027**. `IEdgeEndpoint` gains a **fourth** shape, `AutoPortEndpoint { ComponentId }`, and **ADR 0005's rejection of unnamed anchors is narrowed rather than reversed** — after the side rule below every attachment is still a named port, and what changes is who names it.

**The case earns itself on a defect, not on the reference bar.** `CompletePortDrag` measures `PortHitRadius = 10` **board units** to an actual port point, so a drop anywhere on the body of a shape larger than roughly 20×20 units misses all four border centres and becomes a `FloatingEndpoint` at the drop point — sitting inside the shape, looking attached, tracking nothing. Move the shape and the edge end stays behind. The gap the ticket described as expressive was producing a wrong answer, which is what justifies acting where four tools agreeing would not: ADR 0005 diverged from convention for a stated reason and that reason still holds.

**A shape, not a `PortId.Auto`.** The codebase had already faced this and written the answer on `PortEndpoint` itself, choosing a separate shape for `CustomPortEndpoint` over widening the field. The sharper argument is that `PortId.Auto` needs **five separate exclusions** — `FractionOf` has no fraction, `All` must not list it, `FindPortNear` must skip it, `ComponentContainer` must not draw it, ADR 0010's arrow keys must step over it — to make one member of a fractional-position enum mean "has no fractional position".

**It carries the id and nothing else, which is also the answer to the ticket's fourth bullet.** An anchor on the endpoint would be a second fractional-attachment representation with a different owner, computing `Bounds.PointAtFraction` down a second path for the same result; tldraw carries one because its promotion is *in-gesture* (drag inside the shape and the binding sharpens to the point under the pointer), where this model's precise path is a different drop target, so nothing is in flight to preserve. ADR 0016 settled the same shape of question the same way. So **custom ports survive**, and the cost is stated: you cannot say "two-thirds along the bottom edge, and don't make a port for it" — you take auto, or spend one port-strip double-click on a port that is then addressable. Excalidraw's per-endpoint handle is cheaper in persisted state and is declined. `IEdgeEndpoint` gains one member, `Guid? ComponentId`, collapsing `MissingComponentIds`' two near-identical blocks (which this case would have made three) and giving ADR 0013's interior-edge test an accessor — a marker interface becoming a real one, declared rather than discovered later.

**"Side" means a standard port, not a point on the border.** This was the fork the ticket did not name, and the answer came from the constraint that *all edges connect to the side of a component, none to the centre — this is why we have ports*. Resolution is two-phase: every endpoint has a **reference point** (a port endpoint its port point, a floating endpoint its own point, an auto endpoint its component's **centre**), and an auto endpoint then attaches at the standard port on whichever side the aiming line from its centre to the other end's reference point crosses. That pays four times over — **no new geometry** (choose a `PortId`, then the existing `FractionOf`/`PointAtFraction` path), **no new gap** (the library knows only `Bounds`, so a crossing point would leave an auto edge on a circular component short of its outline at the diagonals, where a standard port position is exactly where a pinned endpoint already sits), **the router never learns auto exists** (both attached kinds hand it a `PortId`), and **auto and pinned become the same geometry** differing only in whether the choice is re-made. The accepted cost is that it **flips rather than slides** — four visible flips per orbit, more noticeable than the corner-sticking that ruled out nearest-point, and two auto edges arriving from similar directions overlap exactly. **The centre is never an attachment**, only an aiming reference; the one crossing-free case (the other end inside the rect) takes the nearest side, which from an interior point is always a face and never a corner, so the rejected rule survives exactly where its failure mode cannot occur. Ties break in `StandardPorts.All`'s order, making the rule total over coincident centres and zero-area rects with no special case. **Auto never chooses a custom port.**

**Resolution becomes pairwise**, which is the structural price: an auto endpoint cannot resolve alone, so `Board.ResolveEndpoint`'s unary signature gains the other end and both of ADR 0020's named entry points inherit it. No circularity and no iteration — both reference points are centres, which depend on no attachment, so both-ends-auto resolves in one pass.

**Three drop zones**: a port's hit radius pins, anywhere else over a component goes auto, nothing floats. The ordering is the point — **the easier gesture gives the more forgiving result**, where today you must hit the small target to get an endpoint that tracks anything at all. Zone 2 reuses ADR 0017's press margin rather than inventing a second notion of "over a component"; a locked entity is not a drop target, falling through; and **the same-endpoint guard widens to same-component**, because structural equality cannot catch `AutoPortEndpoint(A)` against `PortEndpoint(A, Top)` and today's guard would happily create an edge from A's top port to A's own auto endpoint, resolving back to roughly that same port. Both rules apply to `ApplyEdgeEndpointEdit`, so dragging an existing end onto a body converts it.

**A single drag can only produce auto at the target**, since `StartPortDrag` begins from a port and a body drag is ADR 0018's `MoveSelection` — and the type system already agrees, `PortRef` being a closed `Standard | Custom` union that needs no third case. Auto at the source stays reachable in two gestures. Whether a connector drag should be startable without naming a port is handed to ticket 06.

**The drop resolves in C#, and this reverses the session's first recommendation.** ADR 0017's classification cannot serve it in any case: ADR 0018 holds pointer capture for the whole gesture, so a captured `pointerup` is dispatched to the capture element rather than to what the pointer is over. The initial argument for JS was ADR 0017's own — geometry is blind inside an author's component — and **that argument does not transfer**, because `instance` and `author-content` fall in the *same zone* here. With it removed C# wins on every axis: the resolver is a pure function of `Board`, a point and the scale, so port-versus-body is assertable in xUnit where JS would have made it browser-only (ADR 0025 paid real cost for exactly that property); `.selection-bounding-box` cannot swallow a drop from the shape the drag started on, which under `elementFromPoint` it would have, being a real hit region above every selected target; the concentric resize-handle collision cannot misdirect a drop, settling it for this gesture without waiting on ticket 06; and ADR 0018's release payload gains nothing. The z-order argument for JS is weak too, since instance stacking is *driven by* `ZIndex` in CSS, so C# sorting by `ZIndex` agrees with what the user sees by construction. The one real objection — the same circle described twice, in CSS and in C#, free to drift — is closed by **`N` living in C# and publishing through `ContentStyle`** as `--d12-scale` already does, which also makes `PortHitRadius` `N / scale` and delivers the screen-pixel correction ADR 0025's relationship test asked for. The asymmetry left behind is principle: **the press classifies in JS because it needs the DOM and must decide before the interop hop; the drop resolves in C# because it needs `Board`, carries no synchronous obligation, and should be provable without a browser.**

**Routing and endpoint kind stay independent**, and the ticket's third bullet dissolves rather than resolving. The reference coupling (Figma's magnets-by-line-type, Excalidraw's elbow-only midpoints, tldraw's elbow-only handles) describes **what a router reads** — an elbow must choose a direction to leave a shape, a straight line has none to choose. **Ours reads neither.** `EdgePathD` is unconditionally horizontal-first, so an orthogonal edge attached to a `Top` port leaves it **sideways** and immediately turns, and `Curved` bends on the same `midX`. So `Straight` + `PortId.Top` is not ill-formed at all, it is the everyday case; `Orthogonal` + any port is broken, and broken because the router ignores the side. A legality rule would **hide** that, and coupling would make `ChangeEdgeStyleCommand` coerce endpoints — a style command rewriting what an edge connects to, with undo restoring attachments the user never touched. Carried out as [Direction-aware orthogonal and curved routing](42-direction-aware-edge-routing.md). Auto in fact gives such a router **better** input than a named port: its side is derived from where the other end is, so it can never face away.

**The keyboard's guessed side becomes a derived one.** `OnEnterPressed` seeds `PortEndpoint(id, PortId.Top)` — an arbitrary side, guessed and pinned, this ticket's own defect in another input path. The seed becomes auto, with **no new binding**, because the keyboard already has the pointer's two-stage shape: the pointer distinguishes by *where you release*, the keyboard by *how far you drill*. Auto joins the **front of the `Space` cycle** (a state you can leave but not re-enter is a trap), with the list built at the call site — `FindPortNear` shares `Board.AllPorts` and must never see an entry with no fixed point to measure against. Without this the pointer could express an endpoint kind the keyboard could not, which is the gap ADR 0026 exists to close.

**Persistence needs no new field and cannot have a version bump.** `EdgeEndpointEnvelope`'s discriminator has exactly one unreachable combination — `ComponentId` present, `PortId` and `CustomPortId` both null, currently falling through to `throw new JsonException("neither port-attached nor floating")` — and that combination already means *a component named, no port named*. One switch arm, no format change. And **`EnsureSupportedSchemaVersion` is strict equality, not a floor**, so bumping to 2 would make every board ever saved throw `UnsupportedSchemaVersionException`: ADR 0016 declined a bump by preference, here declining is the only option that does not also redesign the version gate. Old readers already degrade gracefully, `ParseEntries` turning the unknown combination into a `BoardDeserializeWarning` and dropping that one edge.

**Unblocks ticket 06**, and hands it a sharpened question rather than a new one: because ADR 0017's affordances leave the render set and the hit set together, **06's visibility decision is a decision about where pinning is reachable at all** — ports hidden on an unhovered shape means a drop there gives auto, ports shown during a connector drag means it can pin. It also inherits `N` as the number it was already asked to own, and gets the concentric collision settled for this one gesture for free.
