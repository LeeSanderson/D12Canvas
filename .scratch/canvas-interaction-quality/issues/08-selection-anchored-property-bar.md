# Selection-anchored property bar

Type: prototype
Status: resolved
Blocked by: 05

## Question

Decide the shape and placement of a property-editing surface anchored to the selection, replacing or supplementing the docked `PropertyPanel`.

The seed note reports that editing properties — a sticky note's colour, for instance — is not possible, and asks for a bar that pops up above a selected component or group, or below when there is no room above.

The machinery already exists and is substantial: `PropertyPanel` builds editors generically from each component type's `EditableProperty` schema, with the full `EditorKind` set, a `Custom` escape hatch, and cross-type shared-property editing (ADR 0008). What does not exist is any placement other than host-positioned chrome, and `D12Canvas.App`'s `BoardEditor` never mounts it at all — which is why the note reads as "not possible" rather than "badly placed".

Build a prototype and decide:

- Whether this is a new positioning mode on `PropertyPanel`, a distinct component sharing its schema machinery, or a replacement. ADR 0002 keeps chrome separate from board content and positions chrome via the host's own CSS — a selection-anchored bar must track board coordinates through pan and zoom while remaining chrome, which that ADR did not anticipate. Note ADR 0002 is settled, so resolve this within it or establish why it genuinely cannot be.
- Placement rules: preferred side, flip conditions, viewport-edge clamping, and behaviour when the selection is larger than the viewport or partly off-screen.
- Behaviour during a gesture. Does it follow a moving selection live (requires ticket 05), hide for the duration, or freeze? Following looks best and costs the most.
- What it shows for a multi-selection and for a `Group` — ADR 0008 already decided cross-type edits touch only explicitly-tagged shared properties, so the question is presentation, not semantics.
- Whether the docked panel survives alongside it as a host-selectable option, and what `D12Canvas.App` should mount.
- How it interacts with the context menu (10) — both are selection-anchored popovers and must not fight over the same space or the same dismissal gesture.
- Keyboard and focus behaviour: reachability, whether it traps focus, and how Escape is shared with selection-clearing.

- **Whether an edge can be edited here at all**, handed over by [Edge visibility and board-content theming](14-edge-visibility-and-board-content-theming.md). Four `Edge` properties are now settable through `ChangeEdgeStyleCommand` with no surface whatsoever — `RoutingStyle`, `SourceArrow`, `TargetArrow` and (per ADR 0016) `Color` — behind a commit point whose own comment reads "No panel UI calls this yet". They want one surface, not four. The structural obstacle is that `PropertyPanel` cannot represent an edge: every `PanelField` target is a `(ComponentInstance, PropertyInfo)` pair discovered via `ComponentTypeKey` → registry → reflected `TProps` schema, and an `Edge` has neither a type key nor a `TProps`, so `[PanelEditable]` cannot simply be applied to `Edge.Color`. The discovery path is closed to entities rather than missing a case, which makes "does the schema mechanism generalise beyond instances" a question this prototype should size. Note an edge selection also arrives through the exclusive `_selectedEdgeId` slot rather than `SelectedComponents`.

Amends ADR 0008.

## Answer

Recorded as **ADR 0021**. Prototype on branch `prototype/property-bar`, commit `a038c4c`: four variants on the unlinked route `/prototype/property-bar`, `?variant=A|B|C|D`.

**The bar was made to justify itself separately, because the reported defect does not need it.** Editing a sticky note's colour is impossible today because `BoardEditor` never mounts `PropertyPanel`, and variant B (a docked panel, no anchoring) fixes that with no library code at all. The bar earns its place on the split ticket 03 found rather than on the defect's urgency: Miro and FigJam float because their editing is expressive and few-valued, Figma Design docks because its editing is numeric and authoritative, and two of the four ship both surfaces at once. So this **supplements** the panel, and `D12Canvas.App` mounts both.

**Four of the ticket's bullets were already answered by ticket 03's teardown and were not prototyped.** Clamp rather than flip (tldraw is the only published implementation and it slides the bar along the viewport edge). Hide for the duration of a gesture (four independent confirmations, and the reason is not cost: a bar over the object you are dragging occludes the thing you are positioning and its controls are dead mid-drag anyway). Supplement rather than replace. And keyboard reachability as a dedicated key into the chrome plus arrows within it, which is the shape `SelectionContextMenu.HandleKeyDown` already implements, leaving only the chord to ticket 16.

**ADR 0002 is not reopened, because the category the bar needs already exists in the code unnamed.** The ticket asked how a selection-anchored bar can track board coordinates while remaining chrome, and treated ADR 0002 as the obstacle. But 0002 governs *host-placed* chrome, and `SelectionContextMenu` is already something else: rendered by `DiagramCanvas`, a sibling of `.diagram-canvas`, positioned in container pixels, with the reason written into the markup at `DiagramCanvas.razor:233`. Two facts make that the only workable answer rather than the tidy one. **A host-placed bar cannot see an edge selection at all** since `_selectedEdgeId` is exclusive and `SelectedComponents` returns empty whenever it is set, so no public surface exposes it, which fails the one bullet ticket 14 handed over. And the clamp frame is the canvas's own box, which only the library knows. The prototype hit both walls by being host-placed, which is what earned the finding.

**Anchoring needs no DOM measurement of the board, and exactly one of the bar.** `ZoomPanTracker` already holds scale, pan and container size, and the container it measures is the frame chrome is positioned in, so the selection's rect is `bounds.X * Scale + PanX` with no interop. What is *not* available is the bar's own width, needed twice (to centre and to clamp), and there is no CSS substitute since percentages in `left` resolve against the containing block rather than the element. tldraw measures its toolbar for the same reason. That self-measurement is the only new interop this adds. Jitter is real and deferred rather than denied: tldraw carries a 150ms move timeout and a 16px minimum reposition distance, recorded as implementation detail of one rule.

**The load-bearing change was forced by choosing glyphs over text, and it was not in the ticket.** Text labels ship with no schema change (the panel already labels by CLR property name), but a glyph cannot be derived. Not from the name, since `FillColor` is guessable and an author's `Accent` is not. Not from `EditorKind`, since `RectangleProps.FillColor` and `StrokeColor` are both `Color` and would draw the same circle on the most ordinary selection there is. The pair that settles it is sharper than either: **`StickyNoteProps.Color` is a background and `TextProps.Color` is a foreground**, same name, same kind, same CLR type, opposite meaning, so every derivation strategy fails on one pair simultaneously.

So the role is declared, and **`EditableProperty.SharedTag` already is that declaration**: an explicit author opt-in, never inferred from a name, validated across types, and used by no built-in. Its free string becomes a closed `PropertyRole` enum where each member owns a glyph and declares the `EditorKind` and CLR type it expects. An enum is a compile-time constant, so this stays attribute-expressible and the `Custom`-kind restriction does not bite. Seven author-facing roles (`Fill`, `Stroke`, `StrokeWidth`, `TextColour`, `FontSize`, `FontWeight`, `TextAlign`) plus four the library uses for an edge, which need no author-facing exclusion because no author's property is an `EdgeRouting` by accident.

Four things fall out of that reuse. **The bar's membership stops being a curation anyone maintains** and becomes an output of the vocabulary, which correctly leaves `ImageProps.AltText` (prose) and `ObjectFit` (an unlabelled three-way choice) panel-only. **A guard that reads stronger than it is gets fixed**: today a lone type can register a wrongly-tagged property and pass, because the validator compares pairwise against whatever else happens to be registered, so the error surfaces later on an unrelated registration; checking against the role catches it where it is caused. **A hole the "never inferred from name alone" rule does not cover closes**, since that rule stops the framework guessing but does nothing about an author hand-tagging both `Color` properties identically, which passes validation and silently merges a background with a foreground. **And this ticket's own empty state explains itself**: a cross-type selection shows nothing today because no built-in is tagged, and tagging finally pays for itself.

The accepted cost is that adding a role is a library change. That is the price of the library owning the glyph.

**Colour merges its glyph and its control** (filled circle for `Fill`, outlined ring for `Stroke`, underlined letterform for `TextColour`) each painted in its current value, so the glyph shape carries which property and the ink carries the value, and the whole cell is 26px against roughly 100px for a labelled one. A rectangle's bar drops from about 340px to 100px. A role-tagged `Custom` property opens the author's fragment in a **popover below its glyph** rather than inline: inline happens to work for the demo's four-swatch picker but an author's fragment has no size contract, so inline means a bar whose height is set by the worst author or a clipped fragment. Decided rather than prototyped, and flagged as such in the ADR.

**Placement's two hard cases need no rules of their own.** A selection larger than the viewport has an off-screen top edge, so the clamp pins the bar to the top margin; a selection mostly off-screen sideways has its midpoint outside the frame, so the clamp pins it to that side. Both are the clamp doing its ordinary job, which is the argument against keeping flip as a fallback: two placement rules competing for one case is how a bar starts jittering.

**The bar reads the *expanded* selection, which removes a rule rather than adding one.** `SelectedComponents` currently empties its whole result if any id fails to resolve, and a `Group`'s id never resolves, so a selected group of three sticky notes offers nothing to edit, in the panel today and the bar tomorrow. The rule's stated reason is good (a shift-click mixing a grouped member with a standalone instance must not silently collapse to "edit the one standalone instance") but expanding removes the hazard outright: every instance under the selection is a target, so there is no subset to edit silently. The panel inherits the fix. This changes a public surface's contract and is declared in the ADR rather than smuggled in.

**An edge is editable, and `EdgeStyle` is why.** The ticket correctly found the discovery path *closed* rather than missing a case, and the answer is that an edge does not need it: `EdgeStyle` already bundles the settable edge properties as one immutable record for `ChangeEdgeStyleCommand`, which is exactly the props-shaped snapshot reflection is reconstructing for an instance. The seam that makes one surface out of two producers is a **row**: id, role, `EditorKind`, options, current value, and a commit callback the producer closes over. An instance row commits through the props batch, an edge row through the edge-style command, and the bar renders both without knowing which it has. The callback is per-row rather than a shared notion of "target" because the commit shapes genuinely differ: instance props are an immutable record replaced wholesale, edge style is three mutable fields snapshotted into a struct. The prototype was built on this shape and both producers worked against it unchanged. That gives the four settable edge properties one surface where the commit point has read "No panel UI calls this yet" since it was written.

**The bar hides while a context menu is open**, which is the same shape as hiding for a gesture and means neither popover needs the other's geometry. The menu is transient and dies on the next press, the bar persists for the selection's lifetime, and the menu offers nothing the bar does. Two consequences for ticket 10: a right-click on the bar is not a canvas press at all, since the bar sits outside `.diagram-canvas`; and the context menu has **no viewport clamping whatsoever** today, so the clamp rule here is the first of its kind in this codebase and ticket 10 should adopt it rather than re-derive it.
