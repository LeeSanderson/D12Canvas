# Asset storage seam: where binary content lives

Type: grilling
Status: resolved
Blocked by: 09

## Question

Decide whether binary content — a pasted or placed image, and anything like it later — lives inside board content or beside it, and amend ADR 0004 accordingly.

Ticket 09 decided that a pasted bitmap becomes an `"image"` component instance, and deliberately did *not* decide where its bytes go. This ticket owns that, and it is the reason ADR 0004 moved from the map's settled list to its reopenable one — the envelope's shape is exactly what changes if assets stop being ordinary `Props` data.

The default today is a `data:` URI in `ImageProps.Url`, which needs no ADR change at all: `Props` is opaque business data (ADR 0001/0003), and a long string is just a string. Its cost is concrete rather than theoretical. Base64 inflates the payload by roughly a third, and the result lands in three places at once — the in-memory `Board`, the persisted envelope (which `BoardJsonSerializer` round-trips as one whole document, with no streaming path), and ADR 0007's history, where `AddEntityCommand` holds the `ComponentInstance` by reference and keeps an undone image paste resident until the 1000-entry circular buffer evicts it.

The tension is that ADR 0004 drew its boundary at exactly this line: D12Canvas owns the wire format, the host owns the storage medium and timing. `d12canvas-next` ticket 13 then held that line hard, making import/export host-wired only. An asset store is either a widening of what the library's format describes, or a second thing the host owns — and which it is, is the decision.

Decide:

- **Whether an asset is a first-class concept at all**, or whether `Props` holding a `data:` URI is the answer and the cost is simply accepted. Ruling it out is a legitimate outcome; it returns ADR 0004 to settled.
- **Where the bytes live if they are separated** — a new collection in the envelope, a side-car the host is handed alongside the JSON, or a host-implemented store the library only references. The last is closest to ADR 0004's existing boundary and the furthest from working out of the box.
- **How a `Props` field references an asset without the library parsing opaque `Props`.** This is the hard part: nothing may inspect a `TProps` shape to discover that one of its strings is an asset reference. A textual convention (`asset:<guid>`), a registration-declared asset field, or a dedicated `TProps` field type are the obvious candidates, and each pushes cost somewhere different — onto every component author, onto the registration contract, or onto the serializer.
- **What a board without its assets does** — pasted into a tab that never saw them, imported without its side-car, or loaded when a host's store has lost one. ADR 0004's partial-deserialize-with-warnings path is the obvious precedent; whether a missing asset is a warning or a hard failure is not obvious.
- **Whether history stores bytes or references**, and what that means for undoing a paste whose asset has since been evicted.
- **Whether this is `SchemaVersion` 2**, and therefore whether it is the first real migration — ADR 0004 reserved the field and explicitly declined to build a migration chain "until a real second schema version exists". If this is that version, the mechanism it declined to speculate on is now in scope.
- **Whether the seam is image-specific or general.** A host component type could hold a PDF, an audio clip, or its own blob just as easily, and a seam named for images will not survive the second case.

Amends ADR 0004, and feeds whatever implementation ticket carries ADR 0013's image paste.

## Answer

Recorded as **ADR 0032**. Binary content becomes a content-addressed `Asset` table on `Board`, a `TProps` property declares with `[AssetReference]` that it may hold `asset:<id>`, and `DiagramCanvas` swaps that reference for a renderable `data:` URI before it binds props — so a component author writes an ordinary `src` and never learns assets exist.

**The ticket's own hardest constraint was over-reaching, and it is the second time on this map that the over-reaching rule was a ticket's rather than an ADR's.** Bullet 3 says nothing may inspect a `TProps` shape to discover that one of its strings is an asset reference, and calls that the hard part. `EditablePropertySchema.DiscoverFrom` has always reflected over every public property of a `TProps` at registration time, reading attributes to learn what the library may do with each one — so the constraint was false in shipped code the day it was written, and it forbade the mechanism the codebase already uses for exactly this class of question. The rule underneath is narrower and is ADR 0021's own: **the library may read what an author declares and may never infer from a name or a type.** With that substitution the hard part becomes an attribute discovered in a pass that already runs. Ticket 06 hit the same shape from the other side, where a constraint written while charting ruled out the only answer any reference tool ships; the difference here is that this one was contradicted by code rather than by evidence, so it cost nothing to check.

**ADR 0003 is confirmed rather than reopened, on the read-the-ADR-not-the-summary move this map has now made six times.** Its summary says "three flat collections" and forbids a fourth; its decision is flat-and-ID-keyed *versus an ownership tree*, argued end to end from CRDT merge, and an ID-keyed table that nests nothing is the shape that argument asks for. ADR 0003 also pre-reserved an empty `Edges` collection for a ticket it did not own, so a collection arriving later is within its grain. That mattered: had the summary been binding, the whole live-table branch was unreachable and only the boundary transform survived.

**An asset is not an `Entity`, and the identity mechanism says so independently.** It has no bounds, no `ZIndex`, cannot be selected, hit-tested, moved or grouped, and is referenced by entities rather than referencing them. Separately, dedup was the only reason to separate bytes from props at all and dedup requires hashing, after which an assigned GUID is a second identity answering nothing — so the id is `sha256-<hex>` of the content. Every entity id is **assigned** at creation; an asset id is **derived**. Two arguments reached from opposite directions, one about what an asset can do and one about how it is named, and they agree.

**Asset ids never regenerate on paste, inverting ADR 0013's rule for the first reference class on this board.** ADR 0013 regenerates ids across five references precisely so pasted content is distinct from its source; regenerating an asset id would duplicate the bytes on every paste and destroy the only reason the table exists. Paste merges entities under fresh ids and assets under the ids they carry, which is safe because identical ids mean identical bytes.

**Three of the seven bullets dissolved rather than resolving.** History (bullet 5) is answered by the add-only rule: `AddEntityCommand` holds an instance whose props hold a reference, and the ticket's hard case of undoing a paste whose asset has since been evicted cannot occur, because nothing evicts within a session and ADR 0007 makes history session-scoped. `SchemaVersion` (bullet 6) stays 1 — `Assets` defaults to null, the sixth use of `BoardEnvelope`'s "field didn't exist yet" convention — and a bump was not available in any case, `EnsureSupportedSchemaVersion` comparing with `!=` so that moving to 2 throws on every board ever saved. Image-specific versus general (bullet 7) dissolves on the record's own shape: a hash, a mime type and bytes is content-agnostic, and only the built-in `Image` knows about images.

**The ticket understated its own case in one place and overstated it in another.** Understated: it names the persisted envelope as one of three residencies, but `IndexedDbBoardStore` persists a board as a single JSON string through JS interop and ticket 83 wired debounced autosave over that, so a base64 image is re-encoded and re-shipped on every save — the cost is per-save, not per-file. Overstated: a table does not fix history *retention*. Undo an image paste and the bytes stay resident either way, in the table instead of in the command. What it fixes is **duplication**, which is the larger win in practice but a different claim than bullet 5 makes.

**Collection is at serialise time and the table is add-only in memory, because the obvious alternative defeats its own purpose.** Reference counting would have `RemoveEntityCommand` hold the asset so undo can bring it back, which puts bytes in the history buffer — the exact cost this ticket was asked to remove. Add-only makes undo free and means an abandoned image never reaches the file while staying in RAM until reload. Disk is always exactly right; memory is bounded by distinct content the user deliberately added.

**The trap most likely to be mis-implemented is `Edge.Label`.** "Which assets does this entity set reference" is one function with two callers — `Serialize` and ADR 0013's copy, which must carry the selection's assets and not the board's. `Edge.Label` is a full `ComponentInstance` embedded on the edge and absent from `board.Components`, so a loop over components alone silently drops a labelled edge's image from the saved file and omits it from the clipboard. Same class as the `PortDef.Id` regeneration ADR 0013 called out, and missable for the same reason.

**Bullet 4's degradation already ships and is exactly right.** A missing asset is tolerated on both deserialize paths and warned on the partial one, matching the dangling-endpoint precedent rather than the unresolvable-type one, since the content degrades rather than being unrenderable. Leaving the reference unresolved instead of blanking it lands on `Image.razor`'s `@onerror` branch, which says "Image unavailable" — distinct from the "No image" an empty URL gets. Written for a different reason, correct for this one.

**The component contract gains nothing, which is what the resolution route was chosen for.** `DiagramCanvas` already binds `Props` and already knows the declared asset properties, so it hands over a resolved copy built by the same JSON round-trip ADR 0004 uses to bind props. Cached by props **reference identity**, which is exact because `MutateEntityCommand` swaps `Props` wholesale rather than mutating it — so no board revision counter is needed and ADR 0015's unbuilt one gains no second consumer. A component declaring no asset property is resolved by nothing, leaving today's render path untouched. One detail that looks like the rejected value convention and is not: a declared property may legitimately hold `https://…`, so the `asset:` prefix distinguishes a reference from an ordinary URL *within the one declared property*, and no undeclared property is ever examined.

**Costs stated rather than glossed:** memory is add-only for a session, both raw bytes and their encoded `data:` URI exist for anything on screen, there is no size cap because the library has no basis for one and nobody controls what a user puts on their clipboard, and a host-implemented store is not built — the table is the seam one would hang on. Nothing here introduces a tuned number, so ADR 0025's absent manual pass costs this decision nothing.
