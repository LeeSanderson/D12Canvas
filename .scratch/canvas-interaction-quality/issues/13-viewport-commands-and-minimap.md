# Viewport commands and minimap

Type: grilling
Status: resolved

## Question

Design the means of not getting lost on an unbounded canvas: zoom-to-fit, zoom-to-selection, and a minimap.

ADR 0011 made board extent and zoom unbounded in both directions, replacing the old fixed 3000×3000 box and 0.6×–6× clamps. That removed a real constraint and introduced a real hazard — there is currently no way to recover a view once panned or zoomed away from content, and no overview of where content sits. `CONTEXT.md` already names a minimap as a prospective canvas chrome component, so the seam ADR 0002 defines is expected to carry it.

Decide:

- **Zoom-to-fit and zoom-to-selection**: framing margin, whether zoom is clamped for a tiny or single selection (fitting one sticky note to the viewport would be absurd), and behaviour on an empty board.
- **Zoom-to-100%** and whether a "reset view" distinct from fit is worth having.
- Whether these animate. A jump is disorienting on a large canvas; an animated transition needs an interpolation home, and `ZoomPanTracker` currently holds no notion of time.
- **Minimap**: whether it is in scope for this effort at all, or belongs in the fog until the rest lands. If in scope — what it renders (real components, LOD placeholders per ADR 0011, or plain boxes), whether it is interactive (click-to-jump, drag-the-viewport-rect), how it bounds itself over content that is genuinely unbounded, and its own render cost against a dense board.
- Where these are triggered from: keyboard shortcuts (16), a chrome control, or both. If a control, whether it is a new component or joins something existing.
- Whether any of this is board state or purely view state. ADR 0003 holds zoom/pan as unpersisted view state; a saved "home view" would contradict that, so either it is out or ADR 0003's boundary needs an explicit exception — and ADR 0003 is settled.

## Answer

Recorded as **ADR 0015**, with an addendum to ADR 0009 and three new `CONTEXT.md` terms (`Content extent`, `Framing`, `Minimap`). The minimap was kept **in scope** against the recommendation to send it to the fog; the recommendation rested on the teardown surfacing a minimap only for Miro and omitting it from both the load-bearing and not-load-bearing catalogues, which is absence-of-evidence from a document with no navigation section, and on discoverability cutting the other way — the commands only help a user who already knows they exist.

**Three commands, no reset-view.** Zoom to fit, zoom to selection, zoom to 100% (centre-preserving). A reset is not a missing fourth but an anti-feature: it means scale 1.0 at pan origin, and since ADR 0011 removed board extent the origin has no relationship to content, so a board authored at (50000, 50000) would have reset-view *cause* the hazard this ticket discharges. That same argument makes 100% legitimate only because it leaves the centre alone, and it earns its keep as the one canonical rung on a ladder now unbounded in both directions. The overlap with the wheel ticket resolved into a clean seam: **that ticket owns *how zoom changes*, this one owns *where the viewport lands*** — absolute destinations computed from content here, relative increments sharing one curve and one anchor there. On that split the undocumented `PageUp`/`PageDown` step-zoom bindings (in no ADR at all) stay with the wheel ticket rather than being retuned twice.

**Framing lives in `ZoomPanTracker`, and the reason is an artefact, not tidiness.** It is the inverse of `Viewport`, in the class that owns the algebra and the clamps. But the decisive finding is that `SetScale` and `SetPanPosition` each raise `Changed` independently, so any framing built from two calls emits two events and shows every listener — the host callback, the re-render, the minimap — one frame pairing the **new scale with the old pan**: a visible lurch on every fit, worse the further you started from content. Framing also has to know what the clamps did to it, since a fit wanting 8× under a 4× cap must compute pan against the scale it *got*.

**Content is components ∪ resolvable edge endpoints**, an O(n) scan on `Board` over the existing `Bounds.Union`. Components alone is wrong and not subtly: ADR 0009's palette has a built-in connector entry creating an `Edge` with **both** endpoints floating, so a board can hold edges and no components, and a components-only extent reports that board *empty* while the user looks at a connector. Unresolvable endpoints are skipped rather than treated as (0,0), so a deletion cannot drag a fit toward the origin. Edge routing bow and arrowheads are deliberately imprecise — exact extents mean running the router, which is renderer knowledge in a model query, for an error the margin absorbs.

**The same scan restricted to a set is what zoom-to-selection frames** — ADR 0003 deferred subset queries while naming this exact extraction as the intended path. That unification is what closes a hole that would otherwise have shipped: `_selectedEdgeId` is an exclusive slot never mixed into `_selectedInstanceIds` (the nudge code already notes such a selection "has no `Bounds`"), so a selection-bounds implementation reading only instances makes **frame-selection silently do nothing on a selected edge**, with no visible reason. Reading the slot the selection model already has does not widen ADR 0006 — edges still cannot join a multi-selection.

**Margin 0.9, contain-not-cover, centred, fixed constant.** Fractional because a board-space margin is a constant in the unit the command is choosing, and a fixed screen inset — fine at desktop size — eats over half the width of a canvas embedded in a 240px panel, which an embeddable library cannot assume away. Not host-configurable, following ADR 0011's rejection of a knob added for symmetry alone.

**Framing never zooms in past 1.0.** Fitting one 100×100 instance to a 1200×800 viewport wants 7.2×, at which the instance fills the screen and every neighbour is gone — orientation destroyed by the orientation command. So: compute, cap at 100%, centre either way; on small content the command degenerates into "centre it, at 100%", which is the useful behaviour because the request was to *find* the thing. Host clamps compose on top, and a clamped fit still centres on the target's centre — free only because framing sits inside the tracker. Accepted cost: frame-selection can zoom you **out** from 4×. Capping at `max(1.0, current)` avoids the yank but makes the destination depend on where you already were, and predictability beats local optimality for a recovery command.

**Both degenerate cases are strict no-ops.** Empty board: any destination would be invented, and the case against a privileged origin is *stronger* with no content, not weaker. Empty selection: explicitly **not** a fallback to fit, because an empty selection is visually identical to one scrolled off-screen — which is exactly when the key gets pressed — so a fallback silently converts "frame my selection" into an enormous unrequested zoom-out. Menu rows are hidden rather than greyed, per ADR 0014.

**Motion: the state jumps, the pixels interpolate — so nothing in the model learns about time.** The ticket's premise that animation "needs an interpolation home" turns out to be false, because `.canvas-content` **already carries `transition: transform 0.1s ease-out`**. The transform reaches its destination in one `Changed` and the compositor animates it: no interpolation home, no per-frame interop, no per-frame Blazor re-render on the path prior work identified as the bottleneck. A class overrides the ambient transition with ~250ms for discrete framing; `prefers-reduced-motion` costs one media query instead of hand-plumbed C#; **pointer events are suppressed for the flight**, because otherwise C# is at the destination while pixels are in transit and a mid-flight click hits what is *about to be* under the cursor — one property closing a whole ticket-04-shaped class of bug. Grid crossfade and LOD swap resolve instantly at the destination, accepted as a one-off wobble.

**Two findings in the existing markup.** The ambient 100ms transition applies to *every* transform write, so **pointer-driven pan eases toward the cursor rather than being locked to it** — a feel defect that belongs to the wheel/continuous-input ticket, which has been noted there along with the 250ms constant needing a felt check. And `.canvas-content` still declares **`width: 3000px; height: 3000px`**, a leftover of the canvas ADR 0011 abolished: vestigial for rendering, but it looks like a board coordinate space and is not one, which is precisely the wrong thing in view while building a minimap.

**The minimap renders plain boxes and maps content ∪ viewport.** One absolutely-positioned element per component instance — no text, no mounted component, no `LOD placeholder` (whose entire content is text illegible at that scale), and no edges. Fill from the accent the placeholder already takes from the registration contract, so no new contract field. Mapping the **union of content extent and the current viewport** rather than content alone, because a content-only mapping lets the viewport rect leave the minimap exactly when the user is lost; the union is self-quiescent in ordinary use, since panning *within* content leaves the mapping unmoved, and only starts rescaling once you pan outside — when the feedback is wanted. At distance content compresses toward a dot, which is honest and, being clickable, the recovery route.

**The cost trap in that mapping dissolves structurally.** A viewport-dependent mapping appears to make every pan re-render every box; putting the boxes in **board coordinates under one transformed wrapper** — exactly `.canvas-content`'s own trick — makes a pan one transform write on one element. Boxes split from the rect and sit behind a `ShouldRender` keyed on board revision, the trick `ComponentContainer` already uses and whose comment names canvas panning as the very trigger it defends against. So navigating a dense board costs one rect; content costs only on edit. The minimap holds **its own `ZoomPanTracker`** and frames the union with the same primitive — no second implementation, and it inherits the 0.9 margin. No cap and no internal LOD: omitting content is the one thing a minimap must never do, and if box count ever becomes the ceiling the honest fix is a rasterised surface, which means reopening an out-of-scope decision rather than silently dropping content.

**Interactive: click-to-jump and rect-drag, pan only** — no zoom-by-resizing-the-rect (competes for the same pixels, fourth route to zoom) and no selection (a different concept on chrome). Click animates, drag does not, which is the same discrete/continuous split as the framing class. **The drag takes its press/release mechanism from the arbitration model rather than adding its own mouse-up**: ticket 04 proved all six existing gestures leak through exactly that pattern, and a minimap is small enough that releasing outside it is the *common* case, so hand-rolling would reproduce the defect in its worst shape. That leaves the minimap's display independent of arbitration and its drag dependent on it — and makes the minimap the first thing in this effort to exercise arbitration over **chrome** rather than board content.

**Surfaces: `Shift+1` / `Shift+2` / `Shift+0`**, the convention in three of four reference tools with Miro the lone `Alt` outlier. Bound here rather than deferred to keyboard parity — a deliberate divergence from ADR 0014's precedent, which was right for eight actions needing contested chords but would only re-derive one unambiguous convention from the same evidence. They match on `event.code` (`Digit1`/`Digit2`/`Digit0`), so they are layout-independent rather than matching a shifted character; the guard is focus-within-container, and reconciling guards across the whole table stays keyboard parity's. These commands are also what **retires ADR 0009's "right-click on empty canvas opens no menu"** premise — the actions are supplied here, the menu's composition belongs to the context-menu ticket. No zoom-control cluster, and explicitly no buttons on the minimap, which would turn a view into a control panel and bake in a placement ADR 0002 left to hosts.

**Nothing is board state, and the sharpest consequence was not in the ticket.** No home view: fit is *derived*, so there is nothing to store, and ADR 0003 needs no exception — the feature that would have contradicted it is made unnecessary by the command. But with no persisted view state, opening a saved board starts at scale 1.0 and pan origin, and the origin has no relationship to content — so **a board authored away from the origin opens onto empty canvas on every single load**, reaching the hazard without the user panning anywhere. Hence: **the canvas frames all content when a `Board` is first set**, unconditional, unanimated, gated on a known container size (the seam whose await ordering produced this codebase's worst gesture leak) and firing only on a *new* instance, or an unrelated re-render would yank the user back mid-work. This makes the implementation work bigger than it looks: it shifts the opening view of every board-mounting visual baseline, so landing it needs a full Playwright run with baselines folded in.

Surfaced [Viewport inset for host-placed chrome](issues/24-viewport-inset-for-host-chrome.md) — this ticket creates the problem, since fit centres content in the full container rect while hosts float chrome over it, and the minimap adds a third occluder to the palette rail and the coming property bar.
