# Right-button semantics and press-to-drag

Type: grilling
Status: resolved
Blocked by: 01

## Question

Decide what each mouse button means on press, and specifically how right-button drag-to-pan coexists with right-button click-to-open-menu.

Two seed notes, both about presses being interpreted too narrowly today:

**Press should begin a drag.** `ComponentContainer.HandleMouseDown` arms `_isMoving` only when `IsSelected` is already true, so moving an unselected instance requires a click to select followed by a separate press to drag. The reported experience is that shapes are hard to drag; this is why.

**Right-drag should pan the board.** `DiagramCanvas.HandleMouseDown` returns immediately on `e.Button != 0`, so the right button reaches only `HandleContextMenu`, which opens the selection menu when something is selected and otherwise lets the browser's native menu through.

Decide:

- Press-to-select-and-drag semantics. Does a press on an unselected instance select it *and* arm the drag in one gesture? What happens to an existing multi-selection when the press lands on a non-member — does it collapse immediately on press, or only if no drag follows? Shift-press must keep toggling membership without clobbering the result (`HandleClick`'s existing comment documents why plain click and shift-click already differ here).
- How a press that becomes a drag is distinguished from a press that becomes a click. A movement threshold, a time threshold, or both — and the same question for the right button, where the answer decides between panning and opening the menu. `DiagramCanvas` already has a `_dragMoved` flag serving a related purpose; decide whether that generalises.
- What happens on right-press over empty canvas versus over a selection versus over an unselected instance. Today empty canvas yields the browser's own menu, which is almost certainly wrong for a canvas app but is a deliberate current behaviour, not an oversight.
- Whether left-drag on empty canvas keeps panning. It does today, with shift-drag reserved for marquee. If right-drag pans, left-drag on empty space is free to marquee instead — which is what the reference tools generally do (ticket 03 should confirm). This is a behaviour change beyond the seed notes; decide it deliberately.
- Middle button, and whether space-drag-to-pan should exist as a third route.
- How each of these degrades under the touch non-foreclosure constraint, where there is exactly one button.

Supersedes or amends ADR 0009's interaction table.

## Answer

**Pan leaves the primary button.** A plain primary drag on empty canvas draws the selection box; pan moves to the secondary and middle buttons. Recorded as **ADR 0022**. The reference bar is unanimous here (all four tools marquee on a plain primary drag, all four pan on right, middle or held space, and Miro's help centre answers this ticket's own seed note with "click the right mouse button and drag"), but consensus is not the argument. The argument is that **`Shift` cannot be both the selection modifier and the mode modifier on one surface**: ADR 0006 gives `Shift` a selection meaning, and spending it on "draw a band at all" is the entire reason `UpdateMarqueeSelection` carries the comment "Replaces the selection outright... not additive". There is no way to *add* with a band because the modifier that would mean add is already gone. Pan had two spare buttons; the band had none. So the additive marquee is the payoff of the flip, not a bonus, and it lands as a one-place amendment to ADR 0006 (union, not toggle, because a toggling band deselects what it sweeps and the result then depends on the prior selection in a way you cannot predict mid-drag).

**The table's shape is the finding worth carrying forward.** ADR 0017 classifies eleven roles and ADR 0018 maps them onto eight owners; filling in the deferred `canvas` row shows that **the secondary and middle buttons ignore the role entirely**, with `author-content` the one exception each way. So the eleven-way classification is consumed by the primary button alone, and adding a role later cannot silently change what the pan buttons do. The two exceptions are both load-bearing: a secondary press on `author-content` stays `Native` so an author's `<input>` keeps its spellcheck and its own clipboard items (the class of workaround ADR 0017 was pleased to *delete*), and a middle press on `author-content` pans, because otherwise an instance that is mostly a control swallows every pan starting over it — costing only Linux middle-click paste inside an author's textarea.

**Press-to-select-and-drag adopts tldraw's split**: a press on a non-member collapses the selection to it *at press* (the drag must move something, and ADR 0018 requires the press-time decision to be complete, so deferring would drag the previous selection), a press on a member or on `selection-bounds` defers to release (or a multi-selection dies the instant you try to drag it). `Shift` appends at press outside the selection and toggles at release inside it, so ADR 0006's toggle survives verbatim while shift-drag becomes possible. Membership tests the outermost containing entity, which `EffectiveSelectionId` already computes. **The reassurance that makes this cheap was verified rather than assumed: every click outcome is byte-identical to today's.** `SelectComponent` already collapses on a plain click and toggles on shift, and both paths were traced against the new table — the only behavioural change is that a drag now works from a cold press. This is not a selection-model rewrite wearing an arbitration hat. One apparent inconsistency reconciled rather than hidden: ADR 0018 has `SelectEdge` select on *release*, and the rule covering both is that **selection changes at press only when a gesture has an active phase that would act on it** — an edge press has nothing to enable.

**The secondary button changes nothing until release, and that is forced rather than chosen.** Putting pan on the same button means the menu cannot open on press (tldraw documents the identical consequence: right-drag-pan on moves the menu to release). But the sharper consequence is one tldraw does not have to face and this ticket nearly missed: **resolving the selection at press would make every right-drag pan wipe the selection as a side effect**, on the button that is now the main way to navigate. So pan does not need a selection, the menu does, and the selection is therefore established at exactly the moment the menu opens — preserve inside the current selection, replace on an unselected entity, clear on empty canvas, reduced to one predicate (does the press's entity, resolved outward to its group, belong to the selection?). The asymmetry with the primary button is the same principle applied to a button whose drag does not touch content, not an inconsistency. The menu anchors at the **press** point, diverging from tldraw's release point, because ADR 0018 already fixed the classification at press so the menu's contents are decided there; anchoring at release lets position and subject disagree for no gain.

**Suppressing the browser's own menu turns out to be a correctness fix, not a polish item.** `DiagramCanvas.razor`'s conditional `@oncontextmenu:preventDefault="@HasContextMenuEligibleSelection"` lets the native menu through on an empty selection, and an unsuppressed native menu opening mid-right-drag fires the `pointercancel` the Pointer Events spec *mandates* for an opened menu, which ADR 0018 makes revert the gesture: the native menu aborts the pan it interrupted. Suppression becomes unconditional on board content and **is the fifth synchronous role-derived decision in ADR 0018's list, and the first on an event other than `pointerdown`** — declared rather than smuggled, given this map's three prior corrections for summaries reading stricter than their decisions. The `author-content` exception needs no mechanism at all, since `Native` already declines to `preventDefault`. Whether `contextmenu` even fires after a prevented `pointerdown` is engine-dependent in exactly the way ADR 0018 flagged for `dblclick`, and harmlessly so in this direction: nothing depends on it firing, so unlike the `dblclick` case no probe is needed.

**Threshold: 4 screen pixels, one number for both buttons, no timer.** Windows' own `SM_CXDRAG` default and tldraw's value; Excalidraw's 10 is the outlier and publishes no reasoning. Screen pixels, so the same hand movement crosses it at 0.05x and 8x. The cost is stated rather than glossed: a shaky click now commits a 4-pixel move, which under ADR 0020 is a real history entry, so accidental micro-nudges become possible where a cold press previously did nothing. No time threshold, and the slot deliberately left empty — Miro uses long-press for containment selection and touch uses it for the context menu, which this decision has just moved onto a button touch does not have. tldraw's much larger chrome threshold has no counterpart, because ADR 0018 already established that a palette drag arrives via the browser's own drag-and-drop and never reaches the classifier.

**ADR 0018's `pointerId` keying was found to have a gap and is widened.** Keying by pointer covers a stylus touching mid-drag but not a second *button* on the same pointer, which is the same `pointerId` and which right-button pan makes an everyday accident. The release side is worse: `pointerup` fires per button, so primary-down, secondary-down, primary-up delivers a `pointerup` with a button still held. A gesture now records its claiming button and only that button's release ends it; every other button's down and up is dropped. Not treated as a cancel, because Escape already routes there and two abort routes leave a user unable to tell which they invoked. A middle press that never moves does nothing, having no click outcome to define.

**Touch needs nothing built, because ADR 0018 predicted this exact table.** Its rejection of "every gesture reachable by a plain primary press" was written against precisely this outcome, so the touch table **inverts the `canvas` row** (one finger pans, the selection box becomes the gesture needing a mode) and every other row transfers unchanged. Two tables, already accepted as costing nothing.

**Three things deliberately not decided here, each with a reason and a home.** *Press-through* with the platform accel modifier is a genuine hole — a band can only start on empty canvas, and ADR 0017 widened the problem by making the multi-selection box a solid hit target that consumes presses beneath it — but Ctrl is the reference bar's snap-suppression key and the alignment-guides work has the better claim; noted there, askable again after. It also could not have used Ctrl without a platform check, since **Ctrl+click is the macOS secondary click**, so `DiagramCanvas.razor.js`'s existing `(event.ctrlKey || event.metaKey)` is right for keyboard shortcuts and wrong for a pointer modifier — the same shape of split ADR 0018 already made for its two target guards. *`Shift` as an in-gesture axis lock* composes fine (the threshold separates it from shift-to-toggle) and still goes to the same ticket, so the whole constrain vocabulary is decided at once. *Alt-drag to duplicate* is not a button-arbitration question in disguise: it is either a ninth member of ADR 0018's closed set or a change to what `MoveSelection` commits, and tldraw's mid-drag toggle needs history that can rewind a partly-committed gesture, which ADR 0007 does not provide. Ticketed.

**Held space and a Hand tool are both rejected outright**, not deferred. Space costs a `preventDefault` on its keydown (so space stops scrolling a host page whenever the canvas holds focus), a guard keeping it clear of a focused palette entry and a live text edit, and a cursor change to be discoverable — for a gesture with two routes already. A Hand tool would introduce the first entered mode in the product plus the chrome to host it. Consequently **ADR 0009's core claim is strengthened rather than restated**: ticket 03 argued "Select is the only persistent state" had to become held-versus-entered-versus-one-shot to make room for a space quasimode and a hand tool, and rejecting both means no room is needed. The restatement still stands for the one-shot placement gestures ADR 0009 already describes.

Amends **ADR 0009** (its context-menu paragraph replaced wholesale; core claim confirmed and strengthened), **ADR 0006** (additive marquee; shift-click toggle confirmed and given a press-versus-release timing rule), **ADR 0017** (a genuine reversal: a secondary press reaches a locked entity, which its rejected list ruled out pending this decision), **ADR 0018** (fifth synchronous decision; ownership keyed by button; deferred `Pan`-versus-`MarqueeSelect` question discharged). Confirms **ADR 0019** untouched — `Shift` means horizontal pan on the wheel and additive select on the pointer, different events, and leaving Ctrl unbound on the pointer means its wheel meaning has nothing to contend with. Leaves **ADR 0010** untouched but owing one thing to the keyboard-parity work: the menu has moved onto a button, so a keyboard route to it is now missing outright. `CONTEXT.md` gains **`Drag threshold`**, and `Pointer gesture`, `Hit target` and `Locked` each widen.

**Unblocks [Context menu enrichment](issues/10-context-menu-enrichment.md), [Keyboard parity for new gestures](issues/16-keyboard-parity-for-new-gestures.md).** Surfaced [Alt-drag to duplicate](issues/34-alt-drag-duplicate.md), which now blocks [Latched-versus-live modifier semantics](issues/29-latched-versus-live-modifiers.md) — that ticket inherits a smaller table than it expected, since `Shift` gets no in-gesture meaning and Alt is unbound.
