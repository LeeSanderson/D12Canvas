# Keyboard parity for new gestures

Type: grilling
Status: resolved
Blocked by: 01, 07, 09

## Question

Decide what keyboard access this effort's new gestures require, and reconcile the resulting shortcut table.

ADR 0010 established a full keyboard-accessible interaction model: reading-order tab stops with a `Group` collapsing to one stop, focus-follows-selection, zoom-relative arrow-key move, `Alt+Arrow` per-axis resize, `Ctrl+Tab` plus `Space` multi-select, and mouse-free placement and connector attachment. ADR 0011 then amended ADR 0009's shortcut table with `Ctrl+'` for snap-to-grid. Every shortcut passes an `isEditableTarget` guard so it does not fire during inline text editing.

This effort adds gestures that have no keyboard equivalent yet, and changes triggers that ADR 0010 assumed.

Decide:

- Which new capabilities need keyboard equivalents and which legitimately do not. Clipboard and select-all (09) plainly do. Align and distribute (12) plainly do. Alignment guides (11) are a during-drag affordance with no obvious keyboard form — decide whether keyboard nudging should snap at all.
- **The minimap (13) is interactive chrome with no keyboard form at all.** ADR 0015 gave it click-to-jump and rect-drag, and deliberately left keyboard access here. The likely answer is that it needs none — `Shift+1`/`Shift+2`/`Shift+0` already make navigation keyboard-complete, so the minimap is a redundant pointer surface rather than a gap, which would make it correctly non-focusable and `aria-hidden`. But that has to be *decided* rather than defaulted into, because it is the first interactive chrome in the library, and "mouse-only control" is precisely what ADR 0010 set out to eliminate. Whichever way it goes, ADR 0010's tab-stop model says nothing about chrome at all, which is the same gap the property bar hits below.
- The reconciled shortcut table, including collisions with the browser's own bindings and with what ADRs 0009/0010/0011 already claim. `Ctrl+C`/`Ctrl+V`/`Ctrl+D`/`Ctrl+A` are the obvious pressure points. **ADR 0015 already bound `Shift+1`/`Shift+2`/`Shift+0`** for the three viewport commands, so those rows are settled — but it bound them behind a *focus-within-the-canvas-container* guard rather than the table's `isEditableTarget`, which is the same stricter guard ADR 0013's clipboard rows use. That makes three separate guard regimes now live in one table, and reconciling them is this ticket's.
- How the context menu (10) is opened from the keyboard — the Menu key and `Shift+F10` are the conventions, and neither is handled today.
- **Whether menu rows display their shortcuts, which ticket 10 handed here rather than deciding.** The menu ships with no hints at all, so this owns adding them. Two things fall out of that. Every binding this ticket decides has to reach the menu, or the menu becomes the place shortcuts go to be forgotten. And a hint is the first thing in the library that must *render* a platform-dependent string: `(event.ctrlKey || event.metaKey)` is right for matching but a row reading "Ctrl+D" is wrong on a Mac, so this needs a one-time cached "is this an Apple platform" fact from JS. ADR 0022 already flagged needing a platform check for a pointer modifier, so that fact has two consumers and should be established once. Note that ADR 0014's eight align and distribute actions render as a glyph strip rather than eight rows, so their chords ride on a `title` attribute and need no layout change when they arrive.
- How the selection-anchored property bar (08) participates in the focus order, and whether reaching it is a tab stop, a shortcut, or both.
- What the port affordance decision (06) means for keyboard users. If ports become visible on focus rather than hover, that is arguably an accessibility *improvement* over the current hover-dependent affordance — confirm and record it, since ADR 0010's mouse-free connector attachment already depends on ports being reachable without a pointer.
- Whether the press-to-drag change (07) has any keyboard consequence, or is purely a pointer concern.

Amends ADR 0010 and whatever shortcut table ends up superseding ADR 0009's.

**Update from ADR 0024 (ticket 11 resolved):** bullet 1's question is now two questions, and one of them has a deadline attached.

**The nudge *step*.** `Snap-to-grid` is **on by default** as of ADR 0024, so a board's content sits on grid lines out of the box while `NudgeCommand` still steps by a zoom-relative amount that has nothing to do with the grid. A single arrow press therefore takes a grid-aligned entity *off* the grid by default, where before it only did so for the minority who opted in. tldraw makes the nudge step become the grid size whenever grid mode is on, which is the obvious candidate. This is now the more urgent half.

**Whether nudging snaps to *objects* at all.** ADR 0024 gave keyboard nudge nothing, and deliberately: ADR 0020 states outright that keyboard work must not reach for the `Gesture preview`, because a keypress's result is fully determined the moment it is pressed and there is nothing provisional to show, whereas `NudgeCommand` writes through and extends in place. So an object snap on a nudge cannot be built the way the pointer's is. Decide whether it should exist by some other route or not at all, noting that an `Alignment guide` with no gesture to live inside would have to appear and expire on a timer, which nothing in this library currently does.

Two smaller inheritances. ADR 0024 declined a chord for the object-snapping toggle, so the table gains a `Ctrl+'` sibling in the context menu but **not** on the keyboard, and bullet 6's menu-hint work should show the menu row without a hint rather than inventing one. And the platform fact bullet 6 wants established once now has its second consumer built rather than merely anticipated: ADR 0024 puts a real platform check on the pointer path, for the macOS `Ctrl`+click secondary press.

## Answer

Recorded as **ADR 0026**. **ADR 0009's shortcut table is superseded**, not amended a seventh time — it had grown by six addenda across five ADRs, and two of them contradict its own framing.

**One guard, expressed once.** Three regimes were live plus a special case; they collapse into one early return above the `switch`, passing when `activeElement` is inside `.diagram-container`, or nothing is focused and no text selection lives outside it. The listener stays on `window`, and the alternative of moving it to the container is recorded as **behaviourally identical** — a `keydown` targets `activeElement`, so both select the same events; the choice was about where the rule reads. `isEditableTarget` stays per-row because it genuinely varies. **`Enter`'s `isComponentContainerTarget` is reclassified from guard to scope**: ADR 0018 justified the keyboard predicate's narrowness by saying `Enter` on a palette entry must reach native activation, and the palette is outside the container, so the focus rule now covers that — the conclusion stands with one of its two reasons gone. **The unfocused-canvas cases are let through deliberately**, putting the keyboard where ADR 0019 already put the wheel; that fog patch has two consumers now. The one case excluded is a live text selection outside the container, which is not ambiguous and is the exact `Ctrl+C` hazard ADR 0013 built its strict guard for.

**The nudge step follows the grid, and that costs ADR 0010 nothing.** The finding that decides it is that `SnapBounds` targets `DominantGridSpacing()`, not a fixed 20 units — so the step tracks ADR 0011's visible layer and the dominant cell is **always between 6.3 and 63 screen pixels**. ADR 0010 chose a zoom-relative step so a press would not read bigger or smaller as you zoom, and this preserves that in a bounded range rather than reversing it, which the obvious reading ("the step becomes the grid size") would have done. `Shift` keeps meaning ten and lands on one cell of the next coarser rendered layer. **Next grid line, not plus-one-spacing** — the additive version leaves an off-grid entity off-grid forever and skips zero moving left off a near-zero position, and expressing it needs a **third snap primitive**, a directional ceiling and floor, after ADR 0014 already found `SnapBounds` non-reusable. Two hand-offs: the nudge takes whatever point snap anchors (ticket 40's, currently top-left), and each press's delta must be computed against live bounds rather than `NudgeCommand`'s captured `_before`.

**No object snapping on nudge**, and the shape of the argument is unusual: the keyboard already has the *better* mechanism, since ADR 0014's align commands are exact where a snap is tolerance-based. The decisive reason is legibility rather than mechanism — a keypress has no continuous motion, so a snap would travel anywhere from one grid step to a neighbour's far edge with nothing explaining why this press went further than the last, which is ADR 0024's own objection to snapping placement silently. **No momentary keyboard escape from the grid**: `Ctrl+Arrow` is dead on macOS, where the OS takes it for Spaces and Mission Control — the same class of reservation ADR 0010 used to reject `Alt+Tab`.

**Chrome navigation is two rules, not three answers.** A chrome surface enters keyboard navigation only if it offers a capability no other keyboard route provides; where it does, canvas-rendered chrome takes a chord and host-placed chrome takes its natural tab order. **Minimap: nothing, `aria-hidden`** — decided rather than defaulted, and it leans on arrow-key pan being real. **Property bar: `Ctrl+Enter`** (Miro's; Figma's `Ctrl+F6` loses because the whole `F6` family is browser chrome). **Menu: `Shift+F10` and the `ContextMenu` key**, since macOS has no keyboard context-menu convention and no such key. Palette and panel unchanged, now explained.

**Three bindings enter documentation for the first time.** `PageUp`/`PageDown` zoom — ADR 0015 left them to the wheel decision and **ADR 0019 never mentions them**, so nothing owned them. **Arrow keys pan when the selection is empty**, which turns out load-bearing: it is half of what makes navigation keyboard-complete, hence the minimap needing no route. And writing the pan row down exposed a defect — **`PanStep` is 50 board units undivided by scale**, so a press travels 200 screen pixels at 4x and five at 0.1x, against ADR 0010's own reasoning. Corrected to `PanStep / scale`.

**The keyboard menu's two anchors differ, and that is the part most easily got wrong.** ADR 0023 anchors a menu paste at "the press point that opened the menu", generalised to where the user last indicated. A keyboard-opened menu has no press point, and a stored one names somewhere the user has navigated away from — so the paste anchor is the **viewport centre**, which ADR 0013 already states for the pointer-free case, while the menu *draws* at the selection's box. Different questions, different answers. **Focus must return to the opening tab stop**, which nothing does today because only a pointer has ever opened it. And this **closes a hole in ADR 0017** rather than adding a route: that ADR named the property panel as the keyboard unlock route, and the panel is host-placed and optional — ticket 08 found `BoardEditor` mounts none — so a keyboard user on such a host had no unlock route at all, the locked-forever failure ADR 0017's separation rule exists to prevent.

**Chords are assigned by the table's own shape.** Every action on a selection has one — Delete, group/ungroup, the four z-order commands, duplicate — and the rows without are preferences and one family of eight. So **lock takes `Ctrl+Shift+L`**, being the only action-on-a-selection that would otherwise lack one, and ADR 0024's "reachable rather than fast" does not transfer because that was an argument about a preference set once. **The eight align actions take none**: with the menu keyboard-openable they are already mouse-free, ADR 0010's goal is operability rather than a chord per action, eight exceeds what anyone memorises, and **Figma's `Alt`+letter set is not safely available in a browser** — `Alt+D` focuses the address bar in three engines, `Alt+V` and `Alt+H` reach Firefox's menu bar. Nothing else gains one.

**Hints on live bindings only**, with the sharp edge being that **eligibility follows the enabling flag rather than the binding**: `EnableSnapToGridShortcut` disables the chord while ADR 0023 deliberately kept the row working, so that row hints only while the chord is live. One platform boolean cached at init with **two consumers**, the second being ADR 0024's macOS pointer check. Recorded because they will be rediscovered otherwise: there is no clean detection API (`navigator.platform` deprecated, `userAgentData` Chromium-only), and a hint is **two rendering conventions** — Apple concatenates the modifier symbols with no separator in fixed order, everywhere else joins words with a plus, and interpolating a modifier name produces a string wrong on both platforms at once.

**`Ctrl+Tab` is recorded as suspect, not rebound.** ADR 0010 rejected `Shift+Tab` and `Alt+Tab` as captured by browser or OS convention before a page handler sees them, and **that rejection appears to apply to its own choice**: `Ctrl+Tab` switches tabs in Chrome, Edge and Firefox, and since every binding accepts `metaKey`, the Mac reading is `Cmd+Tab`, the OS app switcher. `DiagramCanvasCtrlTabSpaceMultiSelectTests` invokes `OnCtrlTabPressed` directly, so it proves the C# and is blind to the input path — ADR 0025's plumbing rule pointing at a hole. Not rebound because every candidate is reserved somewhere (`Ctrl+Shift+Tab` reverse-switches, `Ctrl+Arrow` is macOS Spaces, `Ctrl+Space` is Windows IME, `F6` is browser chrome), and if none is free the fix is **reopening focus-follows-selection**, since "move focus without selecting" needs a chord only because selection follows focus. **Verification is a `task`, not a probe, and that bounds ADR 0025 a second time**: the observable is whether the *browser* switches tabs, invisible from inside the page, so Playwright would confirm the handler fires and miss the failure. Surfaced as [Whether Ctrl+Tab survives the browser](41-ctrl-tab-browser-reservation.md).

**Two of the ticket's bullets resolve without a decision.** The port affordance question stays with ticket 06, which still changes what affordances exist; what it inherits is a **constraint** rather than a preference — ports must be reachable and visible without hover, because ADR 0010's mouse-free attachment already depends on it in live code. And **press-to-drag has no keyboard consequence**: ADR 0022's additive marquee already has its analogue in `Ctrl+Tab`/`Space`, and its rejection of held-space pan is consistent rather than lucky, `Space` never having been available.

Supersedes ADR 0009's table; amends ADR 0010 in four places, ADR 0014 in one phrase, and ADR 0017's unlock route; confirms ADRs 0011, 0013, 0015, 0018, 0020, 0021, 0022, 0023 and 0024, three of which routed questions here explicitly. `Nudge` and `Shortcut hint` added to `CONTEXT.md`, with `Context menu`, `Minimap` and `Paste anchor` widened.
