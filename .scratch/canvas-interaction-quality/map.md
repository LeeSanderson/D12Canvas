# Canvas Interaction Quality

Wayfinder map.

## Destination

A written spec (PRD) for a full interaction-quality pass on the D12Canvas canvas, backed by amended or superseded interaction-layer ADRs, and carried through to implementation tickets in this same effort. The seed was a list of ten felt defects and gaps from real use of `D12Canvas.App` — each now restated in the ticket that owns it — but the destination is deliberately wider than that list: the canvas should feel like a first-class direct-manipulation surface, not a component library that technically supports the gestures. Mouse and trackpad are first-class; touch and pen are not built, but must not be foreclosed.

## Notes

- Domain: a Blazor DOM/CSS diagramming canvas. Consult `domain-modeling` when naming what this effort introduces, and `codebase-design` when shaping anything structural. The term this Note used to say was missing now exists: **`Pointer gesture`** (ADR 0018), deliberately one word from `CONTEXT.md`'s existing `Gesture` — the history unit — because the relationship between them is load-bearing and four pointer gestures never produce a history entry at all. The arbitration layer itself is decided: polymorphic gesture objects over an explicit context, all owned by `DiagramCanvas`, with `ComponentContainer` holding no gesture state. Note for anyone reading the older tickets: the smear was **four** mechanisms, not three — a parallel `click`/`dblclick` dispatch layer sits alongside the `stopPropagation` directives, the bubble ordering and the nine flags, refereed by `_dragMoved`.
- **Reopenable:** ADRs 0004 (persistence format), 0005 (connector/edge model), 0006 (selection model), 0008 (property panel and layering), 0009 (tool modes and interaction model), 0010 (keyboard-accessible interaction). Supersede rather than accumulate contradictory amendments where a decision genuinely changes.
- **ADR 0004 was moved from settled to reopenable while resolving ticket 09**, and only for the asset-storage seam ([Asset storage seam](issues/23-asset-storage-seam.md)) — pasted image bytes are the first content the envelope has no good home for. Nothing else about the format is reopened by this; the two-phase `Props` round-trip, the versioned envelope and the host-owns-storage boundary all still hold.
- **Settled, not open for re-litigation:** ADRs 0001 (registration contract), 0002 (chrome vs board content), 0003 (board state model), 0011 (unbounded zoom/LOD/grid), 0012 (chrome theming contract). Work within them.
- **ADR 0011 stays settled and was amended in exactly one word while resolving ticket 11** — snap-to-grid's default, off to on. That is not a re-litigation and the distinction is worth carrying: 0011 *states* "an optional, off-by-default toggle" and then never defends the default anywhere, all ten of its rejected alternatives being about persistence, granularity and exposure. So the amendment costs the ADR none of its reasoning. This is the **inverse** of the failure mode two notes below: there, a rule was wider than its argument; here, a rule had no argument behind it at all. Both are found the same way, by reading the ADR rather than a summary of it.
- **ADR 0011 stays settled, and ADR 0017 did not reopen it** — despite making the `LOD placeholder` hittable. 0011's decision names the cost driver as *mounted interactive components* and describes the swap as replacing *the full interactive Razor component tree*; it never says the placeholder cannot be hit. The word "non-interactive" was `CONTEXT.md`'s own, and it has been corrected there. Read the ADR rather than the term before assuming a settled decision blocks something — this is the second time on this map (ticket 14 found the same about ADR 0012) that the summary was stricter than the decision.
- **Non-foreclosure constraint** — binds on the arbitration model ticket: the model must be expressible over pointer/touch input later without redesign. Touch is not being built; it is being kept cheap to add.
- Deliverable spans three projects: `D12Canvas` is the deliverable itself, `D12Canvas.Demo` gains pages so the Playwright suite can cover new visual states, and `D12Canvas.App` gets wired as the acceptance surface (its `BoardEditor` currently mounts neither `PropertyPanel` nor any of this effort's new chrome).
- Standing rule from `AGENTS.md` applies throughout and bites hard here: any change touching rendered markup or a shared `<style>` block requires a full Playwright visual-test run in the pinned Docker image with `-parallel none` before commit. Nearly every ticket in this map touches markup.
- Interaction quality resists paper specification. Prefer `prototype` tickets over `grilling` tickets wherever the real question is "how does this feel" rather than "what are the rules".
- **ADR 0024 is the map's second reversal**, and unlike the first it needs no gesture relearned: snap-to-grid ships on, so every placement and every move now snaps out of the box. The tell is different too. ADR 0022 changes what a gesture *does*; ADR 0024 changes where content *lands*, which nothing in the test suite asserts deliberately but a good deal of it asserts incidentally. Expect placement and move tests plus visual baselines to move, and note that ADR 0014's distribute drift — first entity pinned, last drifting by up to half a grid step — was priced as a minority case and is now the default case.
- **ADR 0022 is this map's first *reversal* of a behaviour a user already has**, rather than an addition or an internal restructuring: a plain left-drag on empty canvas now draws a selection band where it used to pan. Everything else on this map so far has been invisible to muscle memory. Two consequences. Any existing Playwright case that pans by left-dragging the canvas is now asserting the wrong gesture, so a mechanical rename is not enough there — and ticket 04 already found that *every* drag test releases inside its starting element, so the drag suite needs reworking on two axes at once, which is [Verifying interaction quality](issues/15-verifying-interaction-quality.md)'s. And the acceptance surface matters more than usual: this is the first decision that a user of `D12Canvas.App` could dislike on contact rather than merely fail to notice.
- **Check whether a decision's rule is wider than its own reasoning.** This is a distinct failure mode from the summary-stricter-than-the-decision one above, and ticket 10 hit it **twice in one ticket**. ADR 0013 wrote "clipboard access uses the DOM clipboard events, *not* the async Clipboard API" when its reasoning was entirely about the keyboard path, which made a menu row impossible rather than merely unspecified. ADR 0022 wrote `author-content` as `Native` on the secondary button when its reasoning was about *editable* content, which silently took the object menu away from every sticky note. Both were fixed by narrowing the rule to the scope its own argument supports, and neither reversed anything. When a decision blocks something, read its justification and not just its rule.
- **A third variant of the same failure family, and the most dangerous: a rule the framework makes impossible.** The two notes above cover a summary stricter than its decision, and a rule wider than its own reasoning. Ticket 15 found ADR 0018's "entry is `internal`" to be neither — it is simply unachievable, because Blazor requires every `[JSInvokable]` method to be public, and all 20 existing ones on `DiagramCanvas` are. What makes it worth a note rather than a footnote is the failure mode: a non-public `[JSInvokable]` **fails at runtime, not compile time**, so honouring that sentence as written ships a canvas where no pointer gesture works, with a clean build and a green formatter. Read that sentence as covering the arbitration surface (the gesture objects and their context), never the interop entry.
- **Verification is decided, so every implementation ticket now inherits a test shape rather than choosing one** (ADR 0025). Three drive points, and one rule with three faces: probes prove plumbing and never magnitudes, constants are asserted by their relationships and never their values, and performance is asserted by counts and never by clocks. There is **no manual pass**, which is a deliberate choice with a stated cost: nothing in this repo judges whether a tuned number feels right, so a constant introduced by an implementation ticket is defended only by staying ordered against its neighbours.
- **tldraw is a design reference only, never a source of code.** Its `LICENSE.md` requires a commercial licence key and forbids production use without one. Ticket 03's teardown cites its constants and structure as evidence; nothing may be lifted. Excalidraw (MIT) carries no such restriction. Both repositories move fast on exactly the subjects that teardown covers, so it pins tldraw at `ef6e81c` and Excalidraw at `4872083c` — re-verify rather than assume when following a citation.
- **A fourth variant of the failure family, and the cheapest to check: a decision's rejection reason applies to the option it chose.** The three above cover a summary stricter than its decision, a rule wider than its own reasoning, and a rule the framework makes impossible. Ticket 16 found ADR 0010 rejecting `Shift+Tab` and `Alt+Tab` because both are "captured by browser/OS convention before a page-level handler would ever see them" and then binding **`Ctrl+Tab`**, which is the tab-switching chord in three engines and, via the `metaKey` every binding accepts, reads as the macOS application switcher. What makes it worth a note is that the check costs nothing — read the *rejected* list against the *accepted* option, which is one pass over a section already written — and that a whole green test file existed over it, because `DiagramCanvasCtrlTabSpaceMultiSelectTests` invokes `OnCtrlTabPressed` directly and can only ever prove the C#. Unlike the other three variants this one is not resolved on discovery: no replacement chord is free either, so it is carried as a documented doubt with [Whether `Ctrl+Tab` survives the browser](issues/41-ctrl-tab-browser-reservation.md) to establish the fact.

- **A fifth variant of the failure family, and the first that runs the other way: a rejected alternative that is correct once narrowed.** The four above are all about a decision reaching further than it should. Ticket 19 found the mirror image twice in one ADR. ADR 0005 rejected *dynamically-calculated, unnamed anchor points* as **the** attachment model, which is right and stays right — but "auto" is a name, so a calculation that chooses among the *named* points contradicts nothing, and ADR 0027 narrowed the rejection rather than reversing it. Then the specifically rejected rule, nearest-point-on-perimeter, turned out to be exactly correct for the one degenerate case in the new rule, because its failure mode is **corner sticking and corners are exterior-only** — from a point inside the rect the nearest side is always a face. So the check worth carrying is: when a rejected option blocks you, ask whether its stated failure mode has a scope where it cannot occur, and whether the rejection was of the *option* or of the option as the *whole answer*.
- **Check whether an argument imported from another ADR turns on a distinction that matters here.** Ticket 19's first recommendation was wrong for this reason and the correction came from the dev, not from the reasoning. ADR 0017 refused C#-side geometry because the library knows only `Bounds` and goes blind inside an author's component, which is decisive at press, where `author-content` earns different synchronous treatment. Applied to a connector *drop* it collapses: `instance` and `author-content` fall in the **same zone**, so the distinction C# cannot make is one the gesture does not need. With that argument removed the answer flipped, and two things listed as costs of resolving in C# turned out to be costs of the JS route that C# simply avoids. An imported argument is cheap to check — name the distinction it depends on, then ask whether this decision acts on that distinction — and expensive to skip, because it arrives pre-authorised by a settled ADR.
- **`SchemaVersion` is a strict-equality gate, so "bump the version" is never available on its own.** `EnsureSupportedSchemaVersion` throws unless `schemaVersion == CurrentSchemaVersion`, not `<=`, so moving to 2 makes every board ever saved throw `UnsupportedSchemaVersionException` on load. ADR 0016 declined a bump by preference and ADR 0027 declined it by necessity; any future ticket that reaches for one is really proposing to redesign the gate as well, and should say so. What already works instead: `ParseEntries` turns a shape it cannot parse into a `BoardDeserializeWarning` and drops that one entity, so forward-incompatible content degrades per-entity rather than per-board.

## Decisions so far

- [What the browser actually delivers for trackpad input](issues/02-trackpad-input-research.md) — the pinch → `wheel` + synthesised `ctrlKey` convention is real in all three engines, but nothing distinguishes it from a genuine Ctrl+scroll and nothing needs to: both mean "zoom about the cursor", and deriving zoom multiplicatively from `deltaY` (`exp(-deltaY/100)`, Chromium's own inverse) rather than a fixed ±0.1 step handles both device classes in one path. No "gesture ended" signal exists in any engine — a short idle timeout is the portable answer, and it matters for undo granularity, not smoothness. Headline: **`@onwheel:preventDefault` is a silent no-op on the pinned .NET 9 runtime** (Blazor delegates to a passive-by-default `document` listener; the fix landed in 10.0-preview7 and was not backported), so the wheel listener moves into `DiagramCanvas.razor.js` as a non-passive listener on the container — which is the better design regardless of runtime. Pointer Events cannot see a trackpad gesture at all; `gesturestart` would double-count on Safari. Surfaced [Wheel-driven pan and zoom model](issues/17-wheel-pan-and-zoom-model.md).

- [Interaction teardown of reference tools](issues/03-reference-tool-interaction-teardown.md) — Miro, FigJam, tldraw (`ef6e81c`) and Excalidraw (`4872083c`) read against their own sources, organised by gesture. All four classify a press **once, at press, against a hit target**, and separate "pointing at X" from "doing X" with a screen-pixel movement threshold D12Canvas lacks entirely. Confirms ADR 0006's marquee/shift-click, ADR 0008's layering, ADR 0010's tab stops, ADR 0009's one-shot placement — and confirms ADR 0007's one-entry-per-gesture *structurally* via tldraw's mark-based history with no ephemeral write path, which de-risks ticket 05's hardest constraint. Contradicts ADR 0005 hardest: **no reference tool exposes discrete ports as the primary attachment model**, all bind to a normalized anchor with named sides as sugar, and `EdgeEndpoint` cannot express the auto/centre case that matters most. Also finds ADR 0009's "Select is the only persistent state" too strong (held-vs-entered-vs-one-shot is the right restatement) and its empty-canvas no-menu premise now false. Surfaced [Hit-test participation and hit-region geometry](issues/18-hit-test-participation.md), [Edge attachment without a named port](issues/19-edge-attachment-without-named-port.md), [Drag past the viewport edge](issues/20-drag-past-viewport-edge.md), [Create-adjacent-and-connect](issues/21-create-adjacent-and-connect.md).

- [Gesture release reliability: enumerate the leak paths](issues/04-gesture-release-reliability.md) — reproduced in a real browser (harness on `research/gesture-leak-probe`): **all six canvas gestures leak**, and the headline path needs no unusual release location at all. `HandleMouseDown` awaits a `getContainerDimensions` round-trip *before* setting `_isPanning`, so a fast enough click has its `mouseup` processed first and the flag is set on a gesture already over — an ordinary click on empty canvas leaves the canvas panning, invisibly, until the pointer next moves. That one is unreachable by static reading; it is an ordering hazard, not a missing listener. The rest follow from every gesture terminating solely via an `@onmouseup` on one element: release outside `.diagram-canvas` leaks pan/group-move/group-resize/connector; release over any `ComponentContainer` leaks the marquee *entirely inside the canvas*, whose `@onmouseup:stopPropagation` swallows it; and a dragged instance released past the `overflow: hidden` clip edge both leaks and never fires `OnMoved`, so the move never enters history — Ctrl+Z afterwards deleted the instance instead. A leaked connector drag then consumes the next click as its drop point, silently writing an edge. Ruled out: the 197px strip below `.diagram-canvas` is *not* dead (`.canvas-content` overflows into it and still hit-tests). Escape clears only the connector drag; a leaked marquee hijacks the next plain drag before any recovery. **No existing Playwright test could ever have caught any of this** — every drag test releases inside the starting element and none moves the pointer afterwards, which ticket 15 now has as an explicit test shape. Also found the standard ports and edge resize handles are exactly concentric with the handles winning on paint order, so a port is unpressable at its own centre (evidence for [Hit-test participation and hit-region geometry](issues/18-hit-test-participation.md) and [Port affordance model](issues/06-port-affordance-model.md)). Surfaced [Gesture cancellation and revert semantics](issues/22-gesture-cancellation-semantics.md).

- [Clipboard and duplication model](issues/09-clipboard-and-duplication-model.md) — **the system clipboard is the only clipboard** (no internal one, so nothing can go stale), carrying ADR 0004's board envelope *verbatim* in `text/plain`, recognised structurally — no new format, no second serializer, and pasting a saved board's text merges it in. Access is via the DOM `copy`/`cut`/`paste` events, since the `paste` event is the only permission-free read path in any engine, so **`Ctrl+C`/`X`/`V` are not keydown rows at all**; only `Ctrl+D`/`Ctrl+A` are. What travels is the selection closed over **interior edges** (both endpoints inside the set), groups recursively, ids always regenerated across five references — the missable one being `PortDef.Id`, since `CustomPortEndpoint` names the port's own GUID. Paste lands on the **paste anchor** (pointer, viewport centre otherwise), translating as a rigid body, cascading `+20,+20` only on an unchanged anchor. Duplicate never touches the clipboard — copy-then-paste would clobber the user's real clipboard. Select-all takes top-level entities only, and **edges cannot join a multi-selection**, so select-all-then-delete does not clear a board. No new command type — paste/duplicate/cut are `CompositeCommand`s of existing primitives. Exposed one trap: cut on a lone edge must be a no-op, not a delete, since copy no-ops there. Scope change: deciding where pasted image *bytes* live would amend ADR 0004, so **0004 moved from settled to reopenable** and the seam became its own ticket. Surfaced [Asset storage seam](issues/23-asset-storage-seam.md).

- [Align and distribute commands](issues/12-align-and-distribute-commands.md) — eight actions (six aligns, distribute per axis) computed against the **selection bounds**, with no key object: `_selectedInstanceIds` is a `HashSet`, so "first selected" is not merely unused but unrecoverable, and marquee would fill any such order in hit-test sequence anyway. The finding most likely to be mis-implemented: **`ExpandedSelection()` is the wrong tool here** — every existing multi-entity operation flattens a `Group` to its members, which is invisible for a move (one delta for everything) and destructive for align (a delta *per entity*), so these read the **unexpanded** selection and translate a group as a **rigid body**. Distribute means **equal gaps**, ordered by centre, negative gaps allowed. Thresholds 2 and 3, counted unexpanded, hidden below rather than greyed; a zero-delta align pushes no history entry. **Snap is observed** — reversing the initial recommendation to ignore it — and the move that makes it work is snapping the **target coordinate** rather than the result: snapping each entity's `Bounds` afterwards rounds X, which survives align-left but pulls align-right and align-centre apart. Distribute rounds the *gap* (clamped to one step so it never degenerates into *pack*) and therefore **pins the first entity and lets the last drift**; both extremes stay put only with snap off. `SnapBounds` is consequently not reusable — a scalar coordinate snap is needed. No new command type; eight thin public methods over two private implementations, mirroring the z-order quartet. Recorded as **ADR 0014**. Surfaces are the context menu and keyboard, but this ticket delivers **only the commands**, which leaves it depending on neither [Context menu enrichment](issues/10-context-menu-enrichment.md) nor [Keyboard parity for new gestures](issues/16-keyboard-parity-for-new-gestures.md) in either direction — otherwise it would have sat blocked behind ticket 07 for no reason.

- [Viewport commands and minimap](issues/13-viewport-commands-and-minimap.md) — three commands (fit, selection, 100% centre-preserving) and **no reset-view**, which is an anti-feature rather than a missing fourth: ADR 0011 removed board extent, so pan-to-origin can dump the user on empty canvas. Resolved the overlap with ticket 17 into a seam — **17 owns *how zoom changes*, 13 owns *where the viewport lands*** — leaving the undocumented `PageUp`/`PageDown` bindings there. Framing goes **inside `ZoomPanTracker`** for an artefact reason, not a tidiness one: `SetScale` and `SetPanPosition` each raise `Changed`, so a two-call fit shows every listener a frame pairing the new scale with the **old pan**. Content is components **∪ resolvable edge endpoints** — ADR 0009's palette creates edges with both endpoints floating, so a components-only extent calls that board empty — and the same scan restricted to a set is what frame-selection uses, which closes a hole that would have shipped: the exclusive `_selectedEdgeId` slot means an instances-only implementation makes frame-selection **silently do nothing on a selected edge**. Margin 0.9 fixed; **framing never zooms in past 1.0** (accepting that frame-selection can zoom you out from 4×, because a `max(1.0, current)` cap makes the destination depend on where you already were); both degenerate cases are strict no-ops, empty-selection explicitly **not** falling back to fit, since an empty selection looks identical to an off-screen one. The ticket's premise that animation needs an interpolation home is **false** — `.canvas-content` already transitions `transform`, so **the state jumps and the pixels interpolate**, no per-frame render, reduced-motion free in CSS, and pointer events suppressed in flight so a mid-flight click cannot hit what is only *about to be* under the cursor. Minimap kept **in scope** against the recommendation: plain boxes, no edges, mapping **content ∪ viewport** so lostness stays visible and clickable, with the apparent cost trap dissolving structurally — boxes in board space under one transformed wrapper, split from the rect behind a board-revision `ShouldRender`, so a pan costs one transform write. Its drag takes press/release from ticket 01 rather than a hand-rolled mouse-up, making it the first test of arbitration over **chrome**. `Shift+1`/`Shift+2`/`Shift+0` bound here (3-of-4 convention, matched on `event.code` so layout-independent), deliberately diverging from ADR 0014's defer-to-parity precedent; the commands **retire ADR 0009's empty-canvas no-menu premise**. Nothing is board state — fit is derived, so a home view has nothing to store — but the sharpest finding wasn't in the ticket: with no persisted view state a board authored away from the origin **opens onto empty canvas on every load**, so the canvas now **frames all content when a `Board` is first set**. Recorded as **ADR 0015**. Two existing-code findings handed on: the ambient 100ms transform transition means pan *eases toward* the pointer rather than tracking it (ticket 17's), and `.canvas-content` still declares a vestigial `3000×3000`. Surfaced [Viewport inset for host-placed chrome](issues/24-viewport-inset-for-host-chrome.md).

- [Edge visibility and board-content theming](issues/14-edge-visibility-and-board-content-theming.md) — the ticket's own framing was the thing that needed fixing: an edge falls on **neither** side of ADR 0012's chrome-versus-content line, which is precisely why it ended up with no token *and* no data field. The real line is **who renders the pixels** — a sticky note's yellow is untouchable because an author's component paints it; an edge has no author component, so the library may default it. ADR 0012 never said only chrome may read tokens, so nothing in it is reversed and it stays **settled** (a pointer added, not ticket 09's reopening move); the token layer instead gains its **first content-role token**, `--d12-edge`, deliberately not the `--d12-connector-preview` escape-hatch case. Colour is therefore **data with a token-resolved default**: a nullable CSS colour string joining `EdgeStyle`, so **no new command type** and undo is free, with nullability the one deliberate divergence from every other colour prop (`null` = no author opinion). Persistence is one optional envelope parameter and **no `SchemaVersion` bump** — an old board deserialises to null and renders *more* correctly than when it was saved. The mechanism is the sharpest part: both obvious routes are silently broken (a presentation attribute loses to CSS; an inline `stroke` beats `.edge-line.selected`), so the author colour rides in as an inline rebind of a **separate** `--d12-edge-override`, read as `stroke: var(--d12-edge-override, var(--d12-edge))` — the renderer never learns selection exists, and "null falls through to the token" becomes literally the cascade's own fallback. Headline trap, unreachable by reading the CSS: **`<marker>` content does not inherit the referencing element's stroke**, so per-edge colour would have shipped coloured lines with grey arrowheads; `fill="context-stroke"` fixes it and **deletes a marker def** rather than adding one, since `edge-arrow-selected` exists only to carry a different fill. Selection stays **always the accent** (ADR 0006 makes it transient UI state, hence library-painted), which is the status quo tokenised so no light baseline moves, with the 2→3 width bump kept explicitly as the non-colour cue for an author who picks the accent blue. Contrast becomes a **testable guarantee about the token pair against the backdrop** and explicitly none about an authored colour; bullet 6's "arbitrary component fill" mostly **dissolves on paint order** — edges paint beneath components and are occluded rather than crossing them. Ships **no editing surface**, which is not a gap it creates: three edge properties were already settable behind a commit point commented "No panel UI calls this yet", so colour becomes the fourth behind one missing surface, handed to [Selection-anchored property bar](issues/08-selection-anchored-property-bar.md) along with the finding that **`PropertyPanel`'s discovery path is closed to entities**, not merely missing a case. Folded in as binding implementation scope: **ticket 74 did not in fact sweep all remaining chrome** — `.selection-bounding-box`, `.drag-over-affordance` (a *third* blue) and `.floating-endpoint` are still hard-coded, and the bounding box's byte-identical accent means a host retuning `--d12-accent` **desynchronises it from the marquee** directly above it. Recorded as **ADR 0016**, with a new `Edge colour` term and a widened `Theme token` entry. Surfaced [Themed visual defaults for built-in component types](issues/25-built-in-themed-defaults.md).

- [Hit-test participation and hit-region geometry](issues/18-hit-test-participation.md) — the fork the ticket never named is decided by one fact: **Blazor's `MouseEventArgs` carries no event target**, so no rearrangement of per-element handlers can ever "classify once, at press" — the information is not there, and that omission is the whole root of ticket 01's flag soup. The press therefore resolves in **JS**, on a `pointerdown` listener on `.diagram-canvas`, walking up from `event.target` to the nearest marked element and handing C# a `(role, entityId, part)` classification. Geometry in C# was the trap: the library knows only `Bounds`, so it goes **blind inside an author's component**, and since `.container-content` is `overflow: hidden` the rect *is already* an instance's true region — it pays the price and buys nothing. Not a ranked list (a C#-side table would compete with the DOM's own order, so you click the top thing and something beneath wins), and not an element identity (ticket 17 banked that `preventDefault` must be derived **synchronously**, which is ticket 04's `_isPanning` hazard exactly). Eleven roles; `author-content` among them, which makes the synchronous `preventDefault` one line and **deletes both `ComponentContainer`'s blanket `preventDefault` and `StickyNote`'s `stopPropagation` workaround** — the built-in having been the proof that an arbitrary author's `<input>` cannot focus. Chrome is excluded *structurally* by binding to `.diagram-canvas` rather than `.diagram-container`; what ticket 13 needs from 01 is capture-and-single-release, which is separable from classification. Hit regions become **elements** (the visual painted by a non-participant, since `pointer-events: stroke` cannot be widened), sized `calc(Npx / var(--d12-scale))` off a new custom property `ContentStyle` publishes — leaving 06 the numbers and taking only the edge's own 20 screen px. The headline defect: `LodSizeThreshold = 32` makes a default sticky note a placeholder at **0.16× zoom**, and the placeholder is `pointer-events: none` **and** marquee-skipped **and** Tab-skipped, so past that zoom **the whole board is unreachable by every input path that exists** — at exactly the zoom where grabbing a cluster matters most. **ADR 0011 is not reversed by fixing it and stays settled**: its decision names the cost as *mounted interactive components*, never reachability, so the error was in `CONTEXT.md`'s own wording (ticket 14's move again). Content is never dropped, affordances drop below a floor from render and hit set **together**, entities get a margin not a floor. One participation predicate with two readers (C# decides, DOM reflects), differing deliberately in one respect — the press margin does not apply to the marquee. **Locking taken here rather than graduated**, on direction: locked means *nothing modifies this*, flag on instances and edges but derived for a `Group` (ADR 0008's precedent), no `SchemaVersion` bump (ADR 0016's), a `ChangeLockedCommand` that widens the closed command set by one, **amending ADRs 0013 and 0014** to skip locked entities rather than refuse. The rule that makes it safe and that today's code violates: **pointer participation and keyboard reachability are separate properties**, welded together right now by two hand-written checks. Precedence is *affordances beat content, content follows paint order*, declared as z-indexes in one CSS block; resize handle beats port, and instances always beat edges regardless of the `PreviousZIndex()` bug — which with a 20px hit band stops being cosmetic. Recorded as **ADR 0017**, with `Hit target`, `Hit region` and `Locked` added to `CONTEXT.md`. **Unblocks [Pointer gesture arbitration model](issues/01-pointer-gesture-arbitration-model.md)** — the map's spine, whose four blockers are now all resolved.

- [Pointer gesture arbitration model](issues/01-pointer-gesture-arbitration-model.md) — the ticket counted three interacting mechanisms; there are **four**, and finding the fourth changed the answer: a parallel `click`/`dblclick` dispatch layer (three double-click meanings kept apart by their own `stopPropagation` flags) refereed against the mousedown layer by `_dragMoved`. So the model owns click and double-click too, dispatching off a press count carried on ADR 0017's classification, which deletes every `@onclick`/`@ondblclick` binding on board content and makes **`_dragMoved` disappear rather than be ported** — "was this a click?" becomes "did the gesture release from the `pointing` phase?", which the gesture already knows. It also dissolves a probe instead of surfacing one: nothing will depend on the browser's `dblclick` surviving `preventDefault` on `pointerdown`. **Eight pointer gestures**, committed **at press** with the phase inside them rather than arbitrated at the threshold — the candidate-set alternative leaves a press-to-threshold window where *nothing owns the pointer*, so there is nothing to guarantee release of and a cancellation has no owner to ask. Two members are deliberately degenerate (`SelectEdge` has no active phase, `Native` relinquishes) so all eleven roles map totally onto the owner set with no implicit else-branch; crossing the threshold under a pointing-only owner **abandons** the gesture, as a native button does. Playwright's reach is wider than feared and bounded where ticket 17 said: capture makes the release location meaningless, both cancel channels are script-reachable, and only device physics is out, including **ADR 0019's `Auto` profile, which classifies synthetic wheel input as a mouse every time**. Reduced motion goes **suite-wide** with two non-optional constraints (such a rule may only zero durations, since every baseline then documents the reduced rendering and none the default; and ADR 0015's pointer-event suppression must key off `transitionend`, or reduced motion leaves the canvas dead to the pointer for 250ms with nothing animating), plus **one case deliberately running both paths**. Two of the ticket's own premises corrected: all 26 visual files already pass `ScreenshotAnimations.Disabled`, so screenshots never raced the ambient transition, and no `prefers-reduced-motion` rule exists at all, so the context option is a no-op until ADR 0015's implementation earns it. Recorded as **ADR 0025**, amending 0015 in one place, confirming 0018 (one sentence clarified) and 0020, adding a caveat to 0019, with `Interaction probe` and `Release-reliability case` added to `CONTEXT.md`. Handed on: **CI runs the visual job without `-parallel none`**, so today's gate flakes and proves nothing.

- [Keyboard parity for new gestures](issues/16-keyboard-parity-for-new-gestures.md) — **one table, one guard, and a chord only where nothing else reaches**. ADR 0009's table is **superseded** rather than amended a seventh time: six addenda across five ADRs had made the live bindings unreadable from the table alone, and two of them contradict its own framing. The three guard regimes collapse into **one early return** above the `switch`, and the alternative of moving the listener to the container is recorded as **behaviourally identical** — a `keydown` targets `activeElement`, so both select the same events — which makes the choice about where the rule reads rather than what it does. That reclassifies `Enter`'s `isComponentContainerTarget` from guard to **scope**: ADR 0018 justified the keyboard predicate's narrowness on `Enter` reaching a palette button natively, and the palette is outside the container, so its conclusion stands with one of its two reasons gone. The unfocused-canvas cases are let through deliberately, putting the keyboard where **ADR 0019 already put the wheel** and giving that fog patch a second consumer; the one case excluded is a live text selection outside the container, the exact `Ctrl+C` hazard ADR 0013 built its strict guard for and the only one that is not ambiguous. On the urgent half, the nudge step follows the grid and **costs ADR 0010 nothing**, which the obvious reading would have: `SnapBounds` targets `DominantGridSpacing()` rather than a fixed 20 units, so the dominant cell is **always 6.3 to 63 screen pixels** and the step stays screen-relative in a bounded range instead of becoming a fixed board amount. `Shift` keeps meaning ten and lands on one cell of ADR 0011's next coarser rendered layer. **Next grid line, not plus-one-spacing** — the additive version leaves an off-grid entity off-grid forever and skips zero moving left off a near-zero position — which needs a **third snap primitive**, a directional ceiling and floor, after ADR 0014 already found `SnapBounds` non-reusable. **No object snapping on nudge**, and the argument has an unusual shape: the keyboard holds the *better* mechanism, ADR 0014's align commands being exact where a snap is tolerance-based, with legibility deciding it rather than mechanism — a keypress has no continuous motion, so a snap would travel anywhere from one grid step to a neighbour's far edge with nothing saying why this press went further than the last. Chrome navigation becomes **two rules** rather than three separate answers (a surface enters only if it is the only route; canvas-rendered takes a chord, host-placed takes its tab order), so the minimap gets **nothing and `aria-hidden`**, the bar gets `Ctrl+Enter` and the menu `Shift+F10`. **Three live bindings enter documentation for the first time** — `PageUp`/`PageDown` zoom, which ADR 0015 routed to the wheel decision and **ADR 0019 never mentions**, and arrow-key pan on an empty selection, which turns out load-bearing since it is half of what lets the minimap carry no keyboard route; writing that row down exposed **`PanStep` at 50 board units undivided by scale**, 200 screen pixels at 4x and five at 0.1x, corrected against ADR 0010's own reasoning. The keyboard menu's **two anchors deliberately differ**: it draws at the selection's box but pastes at the **viewport centre**, explicitly not ADR 0022's stored press point, which names somewhere the user has since navigated away from — ADR 0023's "where the user last indicated" does not reach a keyboard invocation. Focus must return to the opening tab stop, which nothing does today. That **closes a hole in ADR 0017** rather than adding a route: it named the host-placed, optional property panel as the keyboard unlock route, and ticket 08 found `BoardEditor` mounts none, so such a host left a keyboard user with no unlock route at all. Chords follow **the table's own shape** — every action on a selection has one, and the rows without are preferences and one family of eight — so lock takes `Ctrl+Shift+L` and the **eight align actions take none**, Figma's `Alt`+letter set being unusable in a browser (`Alt+D` is the address bar in three engines). Hints go on live bindings only, with eligibility following **the enabling flag rather than the binding**, one cached platform boolean with two consumers, and a hint being **two rendering conventions** rather than one interpolated string. Recorded as **ADR 0026**, with `Nudge` and `Shortcut hint` added to `CONTEXT.md` and `Context menu`, `Minimap` and `Paste anchor` widened. Surfaced [Whether `Ctrl+Tab` survives the browser](issues/41-ctrl-tab-browser-reservation.md).

- [Edge attachment without a named port](issues/19-edge-attachment-without-named-port.md) — `IEdgeEndpoint` gains a **fourth** shape, `AutoPortEndpoint { ComponentId }`, and **ADR 0005's rejected unnamed anchors are narrowed rather than reversed**: after the side rule every attachment is still a named port, and only *who names it* changes. The case earns itself on a defect rather than on four tools agreeing — `PortHitRadius = 10` is **board units** measured to a port point, so a drop on the body of anything bigger than about 20×20 units misses all four border centres and becomes a `FloatingEndpoint` inside the shape, looking attached and tracking nothing. A shape not a `PortId.Auto`, which would need **five exclusions** across consumers of the enum to make one member of a fractional-position enum mean "has no fractional position"; the codebase had already made that call once, on `PortEndpoint`'s own comment. It carries **the id and nothing else**, which also answers the custom-ports bullet: an anchor on the endpoint would be a second fractional representation with a different owner, and tldraw only carries one because its promotion is *in-gesture*, so **custom ports survive** with the cost stated. The fork the ticket never named was decided by one constraint from the dev — *all edges connect to the side, none to the centre, this is why we have ports* — so "side" means **a standard port, not a point on the border**: aiming runs centre-to-reference-point, and the attachment is the standard port on the side the line crosses. That buys no new geometry, **no new gap** (a crossing point would leave an auto edge on a circular component short of its outline, where a port position is exactly where a pinned endpoint already sits), a router that never learns auto exists, and auto/pinned as **one geometry** differing only in whether the choice is re-made — paid for by flipping rather than sliding, four visible flips per orbit. **The centre is never an attachment**, only an aiming reference, and the one crossing-free case takes the nearest side, reusing the rejected nearest-point rule exactly where its corner failure cannot occur. **Resolution becomes pairwise** — the one geometry on `Board` that cannot answer for a single endpoint alone — with no circularity, since a centre depends on no attachment. **Three drop zones** (port pins, body autos, nothing floats), ordered so **the easier gesture gives the more forgiving result**, reusing ADR 0017's press margin rather than inventing a second notion of "over a component", and widening the same-endpoint guard to **same-component** because structural equality cannot catch `AutoPortEndpoint(A)` against `PortEndpoint(A, Top)`. **The drop resolves in C#, reversing this session's own first recommendation**: ADR 0017's blindness argument looked decisive and does not transfer, because `instance` and `author-content` fall in the *same zone* here — after which C# wins on browser-free assertability, on `.selection-bounding-box` being unable to swallow a drop from the shape the drag started on, and on the concentric handle collision being unable to misdirect it. `PortHitRadius` becomes `N / scale` with **`N` owned by C# and published through `ContentStyle`**, one circle with one owner. **Routing stays independent** and that bullet dissolves rather than resolving: `EdgePathD` is unconditionally horizontal-first and reads neither field, so an orthogonal edge leaves a `Top` port **sideways** today — a router defect a legality rule would have hidden. The keyboard's seed changes from an arbitrary `PortId.Top` to auto with **no new binding**, the two paths distinguishing pinned from auto by *where you release* and *how far you drill*. Persistence needs **no new field** (the discriminator's one unreachable combination already means "a component named, no port named") and **cannot** have a version bump. Recorded as **ADR 0027**, amending 0005, 0010 and 0017, confirming 0016/0018/0020, with `Auto endpoint` added to `CONTEXT.md` and `Edge` and `Port` widened. **Unblocks [Port affordance model](issues/06-port-affordance-model.md)**, handing it the finding that its visibility decision is now also a decision about where *pinning* is reachable. Split out [Direction-aware orthogonal and curved routing](issues/42-direction-aware-edge-routing.md).

## Not yet specified

- **Implementation tickets for every decision below.** This map follows `d12canvas-next`'s shape: design tickets resolve the fog and seed ADRs, a `spec.md` is written, then implementation tickets land in this same `issues/` directory. None can be phrased until the decisions they implement exist.
- **Cursor and micro-feedback vocabulary.** What cursor appears over each affordance, whether a drag shows a ghost or moves the real element, whether a dimension readout appears mid-resize. The arbitration model half is resolved (ADR 0018), so the remaining blocker is the port affordance model, which still changes what affordances exist — and ADR 0018 sharpened the patch rather than shrinking it, since a `pointing` phase that has not yet promoted is exactly the state a cursor or press-and-hold affordance would express, and nothing currently marks it. ADR 0020 supplied the *numbers* half without shrinking the patch either: a mid-resize dimension readout now has an exact source (the `Gesture preview`, published per frame and equal to what the release commits), so what remains there is purely whether it appears and how it reads. ADR 0017 added a dependant with a deadline attached: a **locked** entity is silently unclickable, with no feedback about why, and every reference tool answers that with a lock badge on hover. **ADR 0022 took the deadline off** without shrinking the patch: a secondary press now reaches a locked entity and selects it, so the failure is recoverable by the route users actually reach for, and the fall-through it produces is a harmless selection band rather than the pan the ADR 0017 note described. A badge is still the right answer and still waits here. ADR 0022 also removed one item this patch would otherwise have owned — rejecting held-space pan means there is no hand cursor and no quasimode state to express — and sharpened ADR 0018's `pointing`-phase note above into its worst case: on the **secondary** button an unpromoted press is about to do something categorically different from the promoted one, opening a menu rather than panning, where on the primary button both outcomes at least act on the same thing. **ADR 0023 shrank the locked half again without emptying it**: the menu now carries Unlock on a locked selection and Unlock All on the canvas menu, so the silently-unclickable entity has two more recovery routes and the badge is down to pure explanation. It also removed a case this patch would have had to cover, by narrowing ADR 0022's `author-content` exception: a secondary press on ordinary author content now opens the object menu rather than the browser's, so there is no longer a class of content whose right-click outcome a cursor would have needed to distinguish. **ADR 0024 took the largest single item out of this patch and left the rest sharper for it**: mid-drag feedback about *where a thing will land* now exists and is decided, as the `Alignment guide`, so what remains here is feedback about the pointer's own state rather than the content's. Two of its decisions add small dependants, neither with a deadline. Ctrl now silently changes what a drag does with nothing on screen saying so, which is the first modifier in the product whose entire effect is the *absence* of behaviour, and `Axis lock` has the same shape one step milder. Both are exactly the "quasimode with nothing to express it" case ADR 0022 removed when it rejected held-space pan, arriving back by a different door. **ADR 0027 put the blocker itself on the frontier** — ticket 06 is now takeable, so this patch is one resolution from being specifiable — and added one dependant of the same shape as those two. A drop on a port and a drop on the body one pixel away now produce materially different edges, one pinned forever and one re-choosing its side, with **nothing on screen saying which you are about to get** while the drag is live. That is the first case on this map where the missing feedback is about a *persistent property of the thing being created* rather than about the pointer's own state, and Miro answers it by making the two drop targets visibly different rather than by anything cursor-shaped.
- **Whether the edges layer belongs in the z-order at all.** Ticket 14 found that `PreviousZIndex()` returns `min - 1` while `.edges-layer` is pinned at `z-index: 0`, so **send-to-back drops a component beneath every edge** — after which edges paint across its fill, the one case ADR 0016's contrast reasoning excludes. Today's arrangement also ties the *first* placed component with the edges layer at 0, leaving DOM order to break it. ADR 0008 settled layering as `ZIndex` arithmetic over component instances and never contemplated a non-instance layer competing in the same stacking context; ADR 0008 is reopenable, so this is legitimately askable. Not yet sharp because the answer plausibly depends on whether edges can ever join a multi-selection, which changes whether an edge is a peer of a component in the z-order or a layer beneath it. **Sharpened, not resolved, by ADR 0017**: an edge's hit region is now a 20-screen-pixel band rather than a 2-unit line, so a component sent to the back would stop being *clickable* wherever an edge crosses it, not merely be painted over. ADR 0017 fixed the hit order independently — instances always beat edges — which buys time but leaves the paint arithmetic untouched, and now means hit order and paint order deliberately disagree in exactly this one case. **ADR 0023 makes the gap user-visible for the first time**: an edge has no `ZIndex`, so the object menu shows a selected edge no arrangement section at all, while a component sent to the back is painted under it. A user who restacks a shape and then looks for the same control on the edge crossing it finds nothing to click, which is a clearer statement of the problem than the arithmetic was. **ADR 0024 adds a third non-instance layer to the same stacking context** — the `Alignment guide` layer, placed above content and below selection chrome — which does not change the question but does end the reading that the edges layer is a one-off. Two layers competing with `ZIndex` arithmetic that never contemplated them is a pattern, and whatever rule settles this should cover both rather than special-casing edges. The clipboard half of the same second-classness went to [Clipboard and duplication for a lone edge](issues/36-edge-clipboard-and-duplication.md), which waits on the same ticket 28 this does.

- **Bidirectional numeric property fields.** Excalidraw's Stats panel fields are simultaneously typeable inputs and drag-to-scrub controls with a declared sensitivity — a third option between ADR 0008's docked panel and ADR 0021's bar that neither contemplates. **Sharpened by ADR 0021 without graduating**: the role vocabulary now names exactly the two properties this would apply to, `StrokeWidth` and `FontSize`, and the bar already gives each a glyph beside a compact control, so scrub-on-the-glyph has an obvious home. Still fog because it is a control treatment rather than a placement question, and because a drag on chrome that is not a `MinimapPan` is a ninth pointer gesture ADR 0018's closed set does not contain.
- **Visual-clamped, hit-unclamped affordance sizing at extreme zoom-out.** Pure screen-constant sizing makes handles swamp the content at 0.05×; tldraw clamps the *drawn* circle at a 0.25 zoom divisor while leaving the invisible target full size. A refinement of ticket 06 rather than a separate question, but sharper than that ticket's "hit-target sizing under zoom" currently states. ADR 0017 built the half of it that is mechanism — `--d12-scale`, plus the rule that a region is an element and its visual is painted by a non-participant, which is exactly what lets the two be clamped independently — and deliberately left ticket 06 the numbers. **ADR 0024's prototype found the mechanism is partly free and partly not**, which splits this patch rather than shrinking it: SVG's `vector-effect="non-scaling-stroke"` makes a *stroke* screen-constant under the canvas transform with no custom property involved at all, while doing nothing for glyph *size*, which still divides by scale. So anything drawn as a stroke has already been solved without `--d12-scale`, and anything with an extent has not. Whether the affordances ticket 06 is sizing are strokes or extents therefore decides which half of this it inherits.

- **Input capture for a canvas embedded in a scrolling host page.** ADR 0019 takes always-capture for the wheel and documents the limitation rather than pre-solving it: while the pointer is over the canvas, the host page cannot scroll. Deliberately deferred until it bites. The obvious middle option is already ruled out — capturing only on zoom would let a trackpad user's plain swipe fall through and scroll the page instead of panning the board. **ADR 0026 gave this patch a second consumer and widened it from the wheel to input generally**, deliberately and in the same direction: its focus guard passes when nothing at all is focused, so an untouched embedded canvas answers `PageDown` and `Ctrl+A` rather than the host page. Consistency across the two input paths was the argument, so whatever settles this should cover both rather than solving the wheel alone. Note the one case ADR 0026 refused to fold in: a live text selection outside the container fails the guard, because a selection is the user pointing at what they mean and is not the ambiguous case the rest of this patch is about.

## Out of scope

- **Rotation, and any change giving `Bounds` an angle.** Ruled out while naming the destination: rotation propagates into hit-testing, port placement, edge geometry and the persistence format, which would reopen ADRs 0003 and 0004 — both of which this effort holds settled. Aspect-lock and proportional multi-resize were bundled with it and go out with it; either may return as a fresh effort.
- **Touch and pen as built, tested features.** Non-foreclosed by the arbitration model, but not delivered here — there is no device-testing story in this repo and standing one up is beyond this destination.
- **Real-time multi-user collaboration.** Inherited from `d12canvas-next`; unchanged. Ticket 03 catalogued the presence and facilitation affordances this covers — cursor chat, spotlight/follow, stamps, timers, voting, comments — recorded there for completeness rather than to reopen it.
- **Containers with real parenting** — Miro frames and containers, FigJam sections, Excalidraw frames. Ruled out on ticket 03's evidence: all four reference tools have them and they are genuinely load-bearing for organising a large board, but membership is a parent/child relationship, and FigJam's own accessibility docs say it outright — "Objects placed inside a section are considered children of that section." That reopens ADR 0003's flat, ownership-tree-free `Board`, which this map holds settled. A fresh effort.
- **Named layers** — Miro's Layers panel with an active layer. Same parenting reason as containers, plus ADR 0008 settled layering as `ZIndex` arithmetic with no grouping-aware stacking.
- **Auto-layout of a connected structure** — Miro's mind map with auto-layout on by default, "Layout nodes", tidy-up into a grid. Ticket 12 covers explicit align and distribute on a selection, which is the tractable part; automatic re-layout of a graph is a problem with its own literature and no shared boundary with interaction quality.
- **Changing the rendering strategy for ephemeral chrome.** tldraw's SDK 5.0 replaced per-affordance React/SVG elements with a single 2D-canvas overlay and said so plainly — a real signal for a DOM-based canvas at scale. But D12Canvas is a Blazor DOM/CSS canvas by definition (settled in `d12canvas-next`), and this effort is about how it feels, not what it paints with. Worth remembering when the performance ceiling next comes up.
