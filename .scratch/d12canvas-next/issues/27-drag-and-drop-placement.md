# 27 — Drag-and-drop placement

**What to build:** An end user drags a type from the palette and drops it on the board: a new component instance appears at the drop point, at the type's registered `DefaultSize`, initialised with its `DefaultProps`. (ADR 0009.)

**Blocked by:** 22 (Canvas renders a Board), 26 (Palette lists registered types)

**Status:** resolved

- [x] Dropping places the instance at the drop point, converted correctly to board coordinates at any zoom/pan
- [x] The new instance uses the registered `DefaultSize` and `DefaultProps`
- [x] The instance is added to the `Board` (a real entity, not a visual-only artifact)
- [x] A drag-in-progress affordance is visible; screenshot case added
- [x] bUnit/xUnit coverage of the placement behaviour

## Comments

`Palette` gains an explicit `[Parameter] public DiagramCanvas? Canvas` reference (ADR 0002's "mirrors `ParentCanvas`" wiring, but as a plain parameter rather than a cascading value, since `Palette` is a host-markup sibling of `DiagramCanvas`, not nested inside it - a cascading value from `DiagramCanvas` can't reach a sibling). Each palette entry button gets `draggable="true"` and an `@ondragstart` that calls `Canvas?.BeginPaletteDrag(entry.Key)` - a no-op when `Canvas` is unset, so `Palette` stays usable standalone exactly as ticket 26 left it.

`DiagramCanvas` gets the other half: a new public `BeginPaletteDrag(string componentTypeKey)` stashes the pending key, and `@ondragenter`/`@ondragover` (both `:preventDefault`), `@ondragleave`, and `@ondrop` handlers on `.diagram-canvas` do the rest. `HandleDrop` resolves the registration, converts the drop point to board coordinates via `(e.ClientX - containerRect.left - PanX) / Scale` (mirroring `ZoomPanTracker.Viewport`'s existing inverse-transform math, fetched fresh via the already-exported `getContainerDimensions` JS call rather than cached from first render, since the container can move on the page without firing the resize listener), and adds a new `ComponentInstance` centered on that point - the drop point is the instance's center, not its top-left corner, matching where the cursor (and the browser's default drag ghost) actually is on release. Falls back to `ComponentContainer`'s own default size (200x150) when a registration has no `DefaultSize` (`ComponentSize` is optional). `DefaultProps` is used directly (not cloned) across repeated placements from the same registration - every shipped `TProps` type is an immutable positional record, so sharing the reference is harmless; revisit only if a future built-in ships a genuinely mutable `TProps`.

**Drag-in-progress affordance** is a separate `.drag-over-overlay` element - not a `box-shadow`/`outline` on `.diagram-canvas` itself - toggled by `_isDragOverBoard` (set on `dragenter`/`dragover`, cleared on `dragleave`/`drop`). `.diagram-canvas`'s own child `.canvas-content` is an opaque, oversized (3000x3000) absolutely-positioned element that paints over any decoration on `.diagram-canvas`'s own box, so the affordance needs its own element painted after it in DOM order to read at all. That overlay is placed as a sibling of `.diagram-canvas` directly inside `.diagram-container` (the grid container) rather than nested inside `.diagram-canvas`: as an absolutely-positioned grid item with no explicit `grid-row`, it sizes against the container's full padding box, sidestepping a pre-existing `.diagram-canvas` sizing quirk (its grid row is `minmax(400px, auto)`, and since `.diagram-canvas` has no in-flow content of its own - only the absolutely-positioned `.canvas-content` - the row's "auto" component collapses to the 400px minimum instead of the full container height). That row-sizing quirk pre-dates this ticket and is otherwise invisible (nothing before now rendered a real box against `.diagram-canvas`'s own geometry), so it's left as-is rather than fixed here.

**Playwright visual test note:** the `DragInProgress_MatchesBaseline` case drives the affordance via a synthetic `dragover` dispatched through `page.EvaluateAsync` with a real `DataTransfer` object, not a live `Mouse.Down`/`Move` gesture. Headless Chromium doesn't repaint the page while an actual native HTML5 drag session is in flight, so a screenshot taken mid-gesture captures a stale frame even though the DOM/CSS state is already correct (confirmed by direct pixel sampling and `getComputedStyle` during investigation) - and a synthetic `DragEvent` needs a real `DataTransfer` or Blazor's event processing silently no-ops. `DroppedInstance_MatchesBaseline` uses a real `Locator.DragToAsync` gesture instead, since it only needs the state *after* the gesture completes.

New `/placement-demo` page (`D12Canvas.Demo/Pages/PlacementDemo.razor`) combines `<Palette Canvas="_canvas" />` and `<DiagramCanvas @ref="_canvas" />` side by side, reusing the existing `demo-note`/`stress-item` registrations. Since `Palette` is declared before `DiagramCanvas` in the markup, its `Canvas` parameter would otherwise receive `null` on first render (the `@ref` capture on `DiagramCanvas` completes after `Palette` already received its parameters) - `OnAfterRender(firstRender)` forces one extra render pass so `Palette` picks up the captured reference. Adding this page's nav link changed the shared layout markup, regenerating the `BoardRenderingVisualTests`/`PaletteVisualTests` baselines exactly as ticket 26 hit when it added `/palette-demo` - both re-verified, the only diff in each is the added nav link.

bUnit coverage (`DiagramCanvasPlacementTests.cs`): drop-point placement using `DefaultSize`/`DefaultProps`, fallback size when unregistered, coordinate conversion under pan and under zoom, a no-op drop with no preceding `BeginPaletteDrag`, two placements from the same registration producing independent `Bounds`, and the drag-over overlay's full show/hide lifecycle across enter/leave/drop. `PaletteTests.cs` gained cases for the `draggable` attribute, a full `Palette`+`DiagramCanvas` round trip (drag start on a palette entry followed by a drop on the wired canvas), and a safe no-op when no `Canvas` is wired.
