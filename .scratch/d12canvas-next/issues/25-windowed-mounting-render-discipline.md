# 25 — Windowed mounting + render discipline

**What to build:** An end user gets smooth pan/zoom on large boards: the canvas mounts only the instances `GetVisible` returns, recomputing the window on pan/zoom/resize (never per frame). Mounted instance containers skip re-rendering when nothing about them changed (skip-if-unchanged as the standard contract), and pan-driven re-renders are throttled. Verified against the virtualization stress-test page, which stays as a permanent dev tool.

**Blocked by:** 22 (Canvas renders a Board), 24 (`GetVisible(viewport, overscan)` query)

**Status:** resolved

- [x] Only instances returned by the viewport query are mounted; instances mount/unmount as the window moves
- [x] The window recomputes on pan, zoom, and resize — not per animation frame
- [x] Instance containers skip re-render when their own state is unchanged
- [x] Pan-driven re-render is throttled
- [x] The stress-test Demo page demonstrates the improvement at scale
- [x] bUnit coverage of mount/unmount behaviour as the viewport moves

## Comments

`DiagramCanvas`'s Board-rendering path now feeds `Board.GetVisible(viewport, overscan)` instead of iterating `Board.Components` directly: a new `VisibleComponents` property (`DiagramCanvas.razor.cs`) is what the `.razor` `@foreach` walks. Both the viewport and the recompute cadence were already sitting in code this ticket just had to wire up rather than invent:

- **Viewport**: `ZoomPanTracker` gained a `Viewport` property — the canvas-space rect currently visible in the container, computed from the existing `PanX`/`PanY`/`Scale`/`ContainerWidth`/`ContainerHeight` state (`-PanX/Scale, -PanY/Scale, ContainerWidth/Scale, ContainerHeight/Scale`). This is exactly the math the ticket-02 stress-test prototype had duplicated inline in `VirtualizationStressTest.razor`; moving it onto `ZoomPanTracker` itself means both `DiagramCanvas` and any consumer (the demo page included) read the same computed viewport rather than re-deriving it.
- **Recompute cadence**: `VisibleComponents` isn't cached — it's evaluated fresh on every render. Since renders are already driven only by pan/zoom/resize (via `ZoomPanTracker.Changed` → `StateHasChanged`), with pan-renders throttled to ~60fps (`PanRenderInterval`, pre-existing from ticket 02's fix), the windowed mount list recomputes on exactly that cadence for free — no new event, no per-frame timer.
- **Skip-if-unchanged + pan throttle**: both already existed (`ComponentContainer.ShouldRender()` and `DiagramCanvas`'s `PanRenderInterval`, ticket 02's fix). Nothing to add here; this ticket's checklist items were already satisfied by the earlier fix and just needed the actual windowing on top.

Added `DiagramCanvas.Overscan` (`[Parameter] public double Overscan { get; set; } = DefaultOverscan;`, default `200`px) — a flat canvas-space margin forwarded straight to `Board.GetVisible`. Sized to comfortably absorb the gap between two throttled pan-renders (at a fast drag, the pointer can move well past a much smaller margin before the next windowed re-render lands) without inflating mount/unmount cost much against the 3000×3000 canvas. `DefaultOverscan` is `public const` specifically so the demo page could reference the same value rather than duplicating the literal.

**Stress-test demo (`VirtualizationStressTest.razor`)**: previously ran its own hand-rolled windowing (`RecomputeRenderedNodes`, a `none`/`tight`/`buffered` three-way split) entirely disconnected from `DiagramCanvas` — a duplicate prototype of the mechanism this ticket now builds into the real product path. Replaced with two variants: `none` (baseline, unwindowed — kept via the pre-existing `ChildContent` + manually-composed `ComponentContainer` path, for contrast) and `windowed` (seeds a real `Board` of `StressItemProps`/`StressItemComponent` instances and passes it to `DiagramCanvas.Board`, with a live `Overscan` number input replacing the old fixed tight/buffered presets). New demo-only registration: `"stress-item"` (`StressItemComponent`/`StressItemProps`) in `D12Canvas.Demo/Program.cs`, parallel to the existing `"demo-note"` registration — named to avoid `CONTEXT.md`'s "avoid: node" (an earlier draft used "StressNode", flagged by review since this is a genuine registered component type, not just an internal demo record).

The demo's "total / rendered" label calls `_board.GetVisible(_diagramCanvas.ZoomPanTracker.Viewport, _overscan)` itself rather than reading an equivalent off `DiagramCanvas` — a deliberate choice, not an oversight: an earlier draft added a public `DiagramCanvas.VisibleComponents` accessor specifically to avoid this small duplication, but reading it from the demo produced a visibly wrong "rendered" count for one render immediately after changing `NodeCount` (empirically: `530` DOM nodes but a `112` label, caught via a throwaway Playwright check before this ticket closed). Cause: `Board`/`Overscan` are `DiagramCanvas`'s own `[Parameter]`s, which only update *after* Blazor finishes the parent's render pass and propagates them down — one render later than the parent's own `_board`/`_overscan` fields, which are already current the instant `OnNodeCountChanged` runs. `ZoomPanTracker` isn't parameter-bound (it's a plain mutable object the child exposes directly, updated by imperative calls/events, not declarative binding), so borrowing its `Viewport` from the parent carries no such lag — only reaching for the `[Parameter]`-derived `VisibleComponents` did. Reverted to computing it directly in the demo; `VisibleComponents` stayed `private` on `DiagramCanvas`.

Manually verified in a real browser (headless Chromium via the existing Playwright plumbing, driven with a throwaway scratch test then discarded): seeding 5,000 components in the `windowed` variant mounted only ~530 `.component-container` elements (HUD-reported DOM count matched the page's own "rendered" label exactly), and panning shifted the mounted count as instances entered/left the window (530 → 633 after one drag). `/board-demo`'s 3 seeded notes still render correctly — comfortably inside the default viewport + 200px overscan, so unaffected by the change.

bUnit coverage added: `OnlyInstancesWithinTheWindowedViewportAreMounted` (an in-view and a far-out-of-view instance on the same board; only the former mounts), `AnInstanceMountsOncePanBringsItIntoTheWindowedViewport` (an instance starts unmounted, then mounts once a pan brings it inside the viewport+overscan), and `AnInstanceUnmountsOncePanMovesItOutOfTheWindowedViewport` (the reverse — an initially-mounted instance unmounts once a pan carries it back out). `ZoomPanTrackerTests` covers the new `Viewport` property directly: full container at default pan/scale, shifts opposite the pan offset, shrinks as scale increases.

**Known limitation, not acted on:** `ZoomPanTracker.Viewport` (and therefore `VisibleComponents`) is `Bounds(0,0,0,0)` for the single render before `OnAfterRenderAsync`'s JS interop resolves the real container size (`ContainerWidth`/`ContainerHeight` default to `0`) — so the very first paint mounts only instances within `Overscan` of canvas-origin `(0,0)`, regardless of true container size. Self-corrects on the very next render (the existing `StateHasChanged()` at the end of `OnAfterRenderAsync`'s first-render branch), so it's a one-frame flash rather than a lasting bug, and it's the same pre-existing lifecycle gap `SetContainerSize`'s pan-constraint math already lives with — not something this ticket introduced. Not worth guarding against here (e.g. assuming full-canvas-visible until the first real viewport arrives, as the old stress-test prototype did) without a concrete report of it being visible in practice.

**Noticed but not acted on:** running the existing `D12Canvas.VisualTests` Playwright baselines (`BoardRenderingVisualTests`) against a clean rebuild of unmodified `main` also fails, with the only diff being Blazor's scoped-CSS `b-xxxxxxxxxx` hash identifiers differing between builds (confirmed by reverting this ticket's changes entirely and reproducing the same failure). Pre-existing rig flakiness, unrelated to this ticket — the actual rendered content (aria-labels, instance count, positions) matched the baseline exactly in both cases. Not investigated further here; worth its own ticket if the visual-test rig is meant to be re-verified locally rather than only at baseline-recording time.
