# Align and distribute act on top-level entities against the selection bounds, and observe snap by rounding the target rather than the result

Align and distribute are explicit commands over a multi-selection — the deliberate counterpart to during-drag alignment guides. Both compute their geometry from the **selection bounds**: the union of the bounds of the currently selected *top-level* entities. There is no key object, no first-selected item and no last-clicked anchor, because `_selectedInstanceIds` is a `HashSet<Guid>` with no recoverable insertion order; supporting an anchor would mean adding ordering or an anchor field to ADR 0006's deliberately minimal selection model, plus a visible indicator and a gesture to set it, to buy a behaviour bounding-box alignment already provides. Marquee selection would populate any such order in hit-test sequence, which is arbitrary from the user's point of view, so the ordering would be a lie even once stored.

**Both commands read the unexpanded selection, where an entry is either a component instance or a top-level `Group`,** whose bounds resolve through `Board.GetBounds(group)`. A group's delta is computed once from its own bounds and then applied to every leaf member, so **a group translates as a rigid body** and its internal arrangement survives; nesting falls out of the existing recursive member walk. This is a deliberate departure from every other multi-entity operation, all of which run through `ExpandedSelection()` and flatten a selected group down to member instance ids. That flattening is invisible for a move, which applies one delta to everything, and destructive for align, which computes a delta per entity — reaching for it would slam each member of a group independently onto the same edge, dissolving the arrangement that made it a group. Aligning *within* a group is therefore not supported, and needs no rule to forbid it: one group is one entity, and align requires two. Reaching inside a group is the click-through-into-group gesture ADR 0006 explicitly left to implementation time, and it is not invented here.

**The action set is eight: align left, centre, right, top, middle and bottom, plus distribute horizontally and vertically.** A tidy-up or auto-arrange action is excluded as a re-layout heuristic that decides row counts and wrap points, which is the auto-layout family this effort holds out of scope. Align-to-canvas is excluded because ADR 0011 left the board unbounded, so "centre on the canvas" has no referent. A separate align-to-grid action is excluded as already expressible: `SnapToGrid` on, plus any align.

**Distribute equalises gaps, not centres** — the whitespace between adjacent edges is made constant, with entities ordered by their current centre on the axis. The two meanings coincide for equal-sized objects and diverge the moment they do not, and equal gaps is what reads as tidy. Equal centres is the variant that would suit a flowchart's connector rhythm, but a *regular* pitch is better served by `SnapToGrid`, which already exists, than by a second pair of menu items. When the objects' combined extent exceeds the selection bounds the gap is negative and they overlap evenly; that is the honest result of the request and one undo away, and refusing it would need a rule the UI has nowhere to explain.

**Align requires two top-level selected entities and distribute requires three**, counted unexpanded so that one selected `Group` of five members qualifies for neither — the same notion of selection size `CanGroupSelection` already uses. Distribute's threshold is definitional rather than defensive: with two entities both are extremes, both are pinned, and there is nothing between to move. Below threshold the menu items are **hidden rather than disabled**, following the existing `CanGroup`/`CanUngroup` items, and a keyboard invocation is a silent no-op. An entity whose delta is zero contributes no command, so **an align that moves nothing pushes nothing onto the history stack** — align-left never moves the entity defining the left edge, and pressing an already-satisfied align a second time must not cost an undo press to get past. This matches the existing skips in `MoveComponent` for a snap that rounds back to where an instance already was, and in `RestackSelection` for an unchanged z-index.

**`SnapToGrid` is observed, using the same zoom-adaptive `DominantGridSpacing()` that drag-snap uses.** That spacing steps by a factor of ten (base 20, step 10), so the snap unit changes with zoom — but it is defined so a grid step stays around twenty screen pixels at any zoom, which keeps the snap displacement bounded at roughly ten screen pixels regardless of how far out the user is. A fixed base spacing would be reproducible but would place results on lines the user cannot see when zoomed out, which reads as snap being broken. The accepted consequence is that the same align on the same selection can land at different board coordinates at different zoom levels; enabling snap is an opt-in to a zoom-relative grid, and drag-snap already struck that bargain.

**Align snaps the target coordinate, not each entity's resulting position.** The target is `snap(bbox edge)`, and every entity's corresponding edge is then set to exactly that value — so alignment stays exact for all six actions. Snapping each entity's `Bounds` after aligning would round the **X** coordinate, which preserves align-left (all X equal, all rounding identically) while pulling align-right and align-centre apart, since differing widths give differing X values that round to different lines. Three of six actions exact and three approximate, with nothing in the UI to explain the difference, is not a model. This does mean `SnapBounds` is not reusable here — it snaps a whole `Bounds`, and what is needed is a scalar snap of one coordinate.

**Distribute rounds the gap to the nearest grid multiple, clamped to at least one grid step whenever the ideal gap is positive.** Without the clamp any row whose natural gaps fall under half a grid step rounds to zero and distribute silently becomes *pack* — a command doing the opposite of its name, and not an exotic case: it is any row of small nodes at a zoom level where the dominant step is 200. When the ideal gap is already zero or negative the clamp does not apply and rounding proceeds normally, including to negative multiples. Because a rounded gap changes the run's total length, both extremes can no longer stay fixed: **the first entity — leftmost or topmost — is pinned, and the last drifts** by up to half a grid step per interval. Pinning the selection's centre instead would keep the selection visually in place, but then nothing is where it was and the first entity's final position depends on how many entities are in the selection. **With snap off, both extremes stay put**; the drift exists only because snapping introduced it.

**No new command type is needed.** One invocation is one `CompositeCommand` over one `ChangeBoundsCommand` per moved component instance — a rigid-body group contributing one command per leaf member sharing that group's delta. `ChangeBoundsCommand` already swaps whole `Bounds` and align only ever changes X or Y, so the existing vocabulary covers it; only the traversal is new.

**The commands are eight one-line public methods over two private parameterised implementations**, with the edge and axis enums kept private — the shape the z-order quartet already has, where four named commands delegate to `RestackSelection` and `ApplyZIndexChange`. They are surfaced in the selection context menu and by keyboard, but **how** a menu that gains eight items stays readable, and **which** chords are assigned, are owned by the context-menu and keyboard-parity decisions respectively, not settled here. The property panel is not a surface for them — it edits properties of a selection, not spatial commands over a set — and no toolbar is introduced. Because the commands are public methods with no chrome of their own, they are buildable and testable independently of either surface.

**Considered and rejected:**
- **A key object anchor** (Illustrator's model: align to the first-selected, last-clicked or largest item) — needs ordering or an anchor field on ADR 0006's selection model, a visible indicator, and a gesture to set it; bounding-box alignment needs none of that and is the whiteboard-tool convention.
- **Equal centres as the meaning of distribute, or shipping both variants** — the regular-pitch case is better served by the existing `SnapToGrid`, and four distribute items spend a menu budget already known to be tight.
- **Reusing `ExpandedSelection()`** — correct for a move, destructive for a per-entity delta, and the obvious code to reach for, which is why it is called out here rather than left to be discovered.
- **Supporting align within a group** — requires the click-through-into-group gesture ADR 0006 punted; specifying it from here would pre-empt that decision.
- **Ignoring `SnapToGrid` entirely**, on the precedent that a multi-selection move already opts out to preserve relative offsets — rejected because snapping the target coordinate, unlike snapping the result, preserves exact alignment and makes the objection moot.
- **Snapping each entity's resulting `Bounds`** via the existing `SnapBounds` — breaks align-right and align-centre, and destroys distribute's equal gaps outright.
- **Snapping the bounding box first and then aligning to it** — coherent for align, meaningless for distribute (snapping the extremes contradicts pinning them, and gaps still would not be grid multiples), so it would split the rule across half the actions.
- **A fixed base grid spacing (always 20) for reproducibility** — zoom-independent, but places results off every visible line when the dominant grid is coarser.
- **Pinning the selection's centre under snap** so drift splits evenly across both ends — keeps the selection visually in place, but makes the first entity's position depend on the entity count.
- **Pure rounding with no clamp** — literal, but lets distribute degenerate into pack.
- **A tidy-up action, align-to-canvas, or a distinct align-to-grid action** — re-layout heuristics, no referent on an unbounded board, and already expressible, respectively.
- **A toolbar** for the eight actions — new persistent chrome this effort did not take on, colliding with the unresolved question of whether the host's board editor needs a chrome-layout rework.
- **The property panel as the surface** — it edits properties, not spatial arrangement, and routing through it would make these commands depend on chrome that may not survive prototyping.
- **Two public methods taking public enums**, so a menu could be built by iterating the enum values — a smaller method count, but it adds two permanent public types to the library's API for a convenience the menu may not use, since its items need per-item labels anyway.
- **Disabling rather than hiding ineligible items** — a greyed row in a menu with no tooltip surface explains nothing.

**Addendum (surfaced while resolving the context menu enrichment ticket):** the readability question this ADR handed on ("**how** a menu that gains eight items stays readable") is answered by ADR 0023, and not with any of the three shapes named there. The eight actions render as **a single horizontal strip of glyph buttons, one row tall**, as a `role="group"` of `menuitem`s labelled by `title`, rather than eight rows, a submenu or a capped list. Every reference tool draws align as icons for the same reason this ADR chose bounding-box geometry over a key object: the icon is a diagram of the action.

The strip changes nothing decided here, and it improves one consequence. The **two and three thresholds become a width change instead of a height change**: six align glyphs appear at two top-level entities and the two distribute glyphs at three, so the hidden-not-disabled rule above stops making the menu grow and shrink by eight rows between selections. That was the sharpest cost of hiding rather than disabling, and it is now confined to rows that were always going to appear and disappear one at a time.

The chord assignment this ADR deferred to the keyboard-parity work stays deferred, and the strip makes that deferral free: a glyph's chord rides on the same `title` that already carries its name, so it arrives with no layout change. ADR 0023 puts no shortcut hints on any row for exactly that reason, rather than hinting the rows whose bindings happen to be settled.

**Addendum (surfaced while resolving the keyboard parity ticket):** the deferred chord assignment is now decided, and the answer is **no chords**. ADR 0026 amends this ADR in one phrase: the eight actions are surfaced in the menu and reachable by keyboard *through it*, rather than by keyboard directly. With the context menu openable by `Shift+F10`, the strip is already operable without a mouse — arrow to it, arrow across, `Enter` — and ADR 0010's goal is that the board be operable without a mouse, not that every action have a chord. Eight is also past the three-to-five chords people hold per application, and Figma's `Alt`+letter set is not safely available in a browser, since `Alt+D` focuses the address bar in three engines and `Alt+V` and `Alt+H` reach Firefox's menu bar. The commands themselves are untouched, which is what building them as public methods with no chrome of their own bought. The glyphs consequently carry an action name and no chord on their `title`, so the deferral above cost nothing and closes at zero as well.
